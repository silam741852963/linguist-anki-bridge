## WP-28 — keigo drill cards as text: tap-build on the phone, converted in place

Status: implemented 2026-10-26; live rollout pending (see Progress).

### Goal

The campaign met cards that are neither vocabulary nor grammar pages
(batches 287 and 289, 2026-10-26). Deck 夕暮れの詞, note type "Cơ bản":

- front: a screenshot of a numbered plain sentence, e.g.
  「7. さっきもらった見積書について、3つ確認したいことがあるんですが。（見積書 mitsumorisho）」;
- back: a screenshot headed "Answer" with one to four business-keigo
  versions, e.g. 「先程ちょうだいした見積書につきまして、3点ほど確認させていただきたいことがあるのですが。」.

The user's decision: **keep them as drills, but as text instead of images.**
Their answers to the design questions (2026-10-26):

> - Answering: **tap-build** (tap chunks of the polite sentence in order, with
>   decoy chunks, graded on the front).
> - Back: **keigo highlight, change notes, audio per answer, English
>   translation**.
> - Front: **sentence + word readings** (the plain sentence, the source's
>   reading hints as furigana, a one-line instruction).

### Where things stand

- 夕暮れの詞 holds 317 image-only "Cơ bản" notes. Some are grammar pages
  (handled by the WP-24 grammar flow: `grammar.py dump/split`), the rest are
  these drills. The exact split is counted as the campaign reaches them.
- No managed note type can hold a drill. The campaign defers each drill note
  with `AGENT: keigo drill card …`; 10 so far (287: 1660552242075 …
  1660552462399; 289: 1660727130495 … 1660727509488). `campaign-session.sh
  start` requeues deferred notes, so they return once this package ships.
- WP-26 planned `Linguist Drill v1` (fields `Kind`, `Language`, `Prompt`,
  `Data`, `Answer`, `Explanation`, `Source`, `Audio`) and a drill document
  kind, but nothing of it is built. Its `build` kind (tap chunks with decoys)
  and its bunsetsu chunker are what tap-build needs.

### Decisions

1. **This package builds the shared drill foundation of WP-26.**
   `Linguist Drill v1`, its template and the drill document kind are made
   here, with one kind, `rephrase`. WP-26 adds its generated kinds to the
   same model later, so no second note type appears.
   - The WP-26 field set is kept. `Audio` holds the per-answer readings
     (several `[sound:]`), so the field stays a list, not one reading.
   - `Kind` = `rephrase`, `Language` = `ja`.
2. **Document kind `LearningContent::Drill`.** Fields of a `rephrase` drill:
   - `prompt`: the plain sentence, without the source's numbering;
   - `instruction`: the target register as one line ("Business keigo");
   - `readings`: the source's reading hints as (word, reading) pairs, e.g.
     (見積書, みつもりしょ), converted from the source's romaji;
   - `answers`: every accepted polite version, in the source's order; the
     first is the build target;
   - `changes`: one entry per keigo change: plain part, polite part, kind
     (formal word, humble, honorific, polite), and a short note
     (さっき → 先程, formal; もらう → ちょうだいする, humble);
   - `translation`: one English line for the meaning;
   - `lesson`, `profile` (WP-27) as in grammar.
   Validation: at least one answer; every `changes` polite part occurs in at
   least one answer; every reading's word occurs in the prompt; the build
   data (decision 4) re-joins to the first answer exactly.
3. **Card layout** (one template, task `Production`).
   - Front: the instruction, the prompt with the reading hints as furigana,
     then the tap-build area.
   - Back: every answer with the polite parts of `changes` highlighted and
     its own play button; the change notes; the English translation; the
     source reference.
   - Furigana only on the hinted words, so the prompt is not over-annotated.
4. **Tap-build, graded on the front.**
   - The first answer is cut into chunks with the WP-26 bunsetsu chunker
     (`linguist-text`); a chunk of 1 character is merged with its neighbour,
     and a sentence gives 4–9 chunks.
   - Decoys: for each `changes` entry, the plain part as a chunk
     (もらった against ちょうだいした, について against につきまして), at most
     3 decoys. Decoys never come from guessing.
   - A decoy that also occurs in another accepted answer is dropped (it is
     then also correct).
   - The learner taps chunks in order. The order is checked against the
     first answer; a full order equal to **any** accepted answer whose
     chunks are all on the board also counts as right. Wrong taps are shown
     at once; the back is rated manually (WP-26 decision 2).
   - Chunk order on the front is shuffled with WP-26's seed (day number and a
     hash of `Prompt`), so front and back agree and the position cannot be
     memorized.
   - Build data is computed at render time on the desktop and stored in
     `Data` (JSON); the template is vanilla ES5, no external script.
5. **Converted in place, schedule kept.** The note keeps its id and its one
   card: an in-place model change from "Cơ bản" to `Linguist Drill v1`, as a
   single-unit grammar revamp does. The source card (ord 0) maps to
   `Production`. The screenshots stay in the source archive and are no
   longer rendered.
6. **Content comes from the agent, not Codex.** In the campaign the agent
   reads both screenshots and the OCR (as for grammar pages) and writes the
   whole drill: prompt, answers with OCR fixed, readings, changes,
   translation. No Codex draft call is spent. Audio is VOICEVOX, one reading
   per answer, reviewed like grammar's per-example audio
   (`AUDIO_CANDIDATE_REVIEW`).
7. **Detection.** The grammar cohort's OCR inspection flags a note whose
   back image starts with "Answer" and whose front is one numbered sentence
   as `DRILL_CANDIDATE` (review severity) instead of
   `GRAMMAR_SEGMENTATION_REVIEW`. The agent confirms it by converting, or
   treats the page as grammar.
8. **Command.** `plans convert-drill PLAN --template ITEM` prints a request
   and `--request FILE` replaces the document's content with the drill
   (keeping sources and archives) and publishes a new revision; it resolves
   `DRILL_CANDIDATE` and `GRAMMAR_SEGMENTATION_REVIEW` of that document. The
   lab helper is `drills.py convert BATCH FILE`, like `grammar.py split`.

### Steps

1. `linguist-text`: the bunsetsu chunker (WP-26 step 1, Japanese only here),
   with tests on the 10 deferred drills' answers.
2. Core: `LearningContent::Drill` with the `rephrase` body, validation,
   the `Linguist Drill v1` model, template (front, back, tap-build ES5) and
   CSS matching grammar v4, render (furigana, highlights, per-answer
   sounds, `Data` build JSON), tags (`drill::rephrase`, `drill::ja`, lesson,
   profile).
3. Application: `convert-drill`, task map Cơ bản ord 0 → `Production`,
   per-answer audio candidates, `DRILL_CANDIDATE` in OCR inspection.
4. Companion: the drill field set and the in-place model change (check that
   the existing change path covers a model with a different field count);
   bump the version and `VERIFIED_COMPANIONS` only if the payload changes.
5. Tests: core render and validation, build data equal to the answer,
   decoy filter, application conversion keeps note and card ids and the
   schedule, template in a headless browser (seeded order equal on both
   sides, right and wrong taps, phone width), desktop scenario on
   disposable Anki (install the model, convert one drill, read back).
6. CLI, docs, CHANGELOG entry per fix.
7. Live, while the campaign is paused for the schema/model step:
   `models install drills`; then the 10 deferred drills come back at the
   next `campaign-session.sh start`, and agent turns convert them and every
   later drill. The user tries 10 on the phone before the rest are applied.

### Done when

- The 10 deferred drills are `Linguist Drill v1` notes with the same note
  and card ids and the same schedule, every answer voiced, and the front
  tap-build works on the user's phone (AnkiDroid or AnkiMobile).
- The campaign converts every later drill without a defer, and spends no
  Codex call on them.

### Progress

2026-10-26, implementation (code complete, not yet live):

- `linguist-text`: `ja::chunks` cuts a sentence into bunsetsu (a content
  word with its particles and auxiliaries; punctuation stays with the chunk
  before it; a one-character chunk joins a neighbour; at most 9 chunks; the
  chunks always re-join to the input).
- Core: `LearningContent::Drill` (`kind` = `rephrase`, `prompt`,
  `instruction`, `readings`, `answers`, `changes`, `translation`, `chunks`,
  `decoys`, `lesson`, `profile`) and `validation::drill_problems`:
  `DRILL_ANSWER_REQUIRED`, `DRILL_ANSWER_DUPLICATE`, `DRILL_CHUNKS_MISMATCH`
  (2+ chunks, none empty, re-join to the first answer),
  `DRILL_DECOY_INVALID` (distinct, not a chunk, not text of any answer),
  `DRILL_CHANGE_UNMATCHED` (polite part in an answer; kind formal, humble,
  honorific or polite), `DRILL_READING_UNMATCHED` (word in the prompt or an
  answer; kana reading). Only `Production` is allowed;
  `translation` is required when the explanation language differs.
- Model `Linguist Drill v1` (version 1), one template `Drill`, fields
  `Prompt`, `Instruction`, `Answer`, `Changes`, `Translation`, `Data`,
  `Kind`, `Language`, `Source`. This differs from the WP-26 sketch: the
  per-answer `[sound:]` sits in each `Answer` item (like grammar v4's
  examples), so no `Audio` field; `Changes` and `Translation` replace
  `Explanation`. CSS: vocabulary v3 plus `drill-v1.css`.
- Render: furigana on the first occurrence of each hinted word (dropped if
  it would cross a highlight), polite parts highlighted in every answer,
  one play button per voiced answer, the change list, the translation, and
  `Data` = `{"v":1,"chunks","decoys","answers"}`. Tags `lab::kind::drill`,
  `drill::rephrase`, `drill::<lang>`, lesson and profile tags.
- Front template (ES5): the board shuffles chunks and decoys with the seed
  (day number and a hash of the prompt text); a tap is accepted when the
  built text is a prefix of any accepted answer; a wrong tap flashes "Not
  next"; Undo; "Correct, after N wrong taps" when the text equals an answer.
  Checked in headless Chromium at 390 px: right and wrong taps, Undo, the
  finished state.
- Application: `drill::build` (chunks from the first answer, a polite part
  that crosses chunks joined into one, one decoy per change by putting the
  plain part back, decoys accepted by another answer dropped, at most 3) and
  `drill::convert`, which publishes through the grammar split path as one
  unit: same document, note and cards; requested tasks and card tasks
  `Production`; task maps cleared so the native history review remaps
  (campaign policy `0=production` for drills); OCR reviews resolved by the
  reviewer who wrote the drill. OCR inspection reports a page whose first
  region is "Answer" as `DRILL_CANDIDATE` (agent code in the campaign
  policy). The audio stage voices each answer; generation refuses a drill
  (`GENERATION_DRILL_AUTHORED`), so no Codex call is spent.
- CLI: `plans convert-drill PLAN --template ITEM` prints a request;
  `--request FILE` converts. `models install|update japanese_drill`
  (or `english_drill`).
- Companion 0.7.0: the `Linguist Drill v1` field set is accepted for
  `install_model` and `create_note`. The in-place model change already maps
  template ordinals and writes every target field, so it covers the change
  from "Cơ bản" (2 fields) to the drill (9 fields). The binary accepts
  companions 0.3.0 to 0.7.0; installing the drill model needs 0.7.0.
- Lab helper: `drills.py convert BATCH FILE` (FILE maps a note to its drill
  as read off the pages).

### Known limits — revisit after all packages

- Tap-build checks against the accepted answers only; another correct keigo
  version is marked wrong. The board holds the first answer's chunks, so a
  second answer can be built only where it shares them.
- Decoys are only the plain parts the source changed; other mistakes
  (wrong humble/honorific choice) are not drilled.
- Ratings stay manual; the front grade is not sent to Anki.
- Chunks come from IPADIC part-of-speech rules; a chunk the learner would cut
  differently is fixed only by writing `chunks` in the request by hand.
- Detection is a heuristic on the OCR ("Answer" as the first region). A
  drill page whose OCR starts elsewhere stays a grammar candidate until the
  agent sees it.
- Only the `rephrase` kind exists; WP-26's generated kinds are not built.
- Not yet run on disposable Anki or live: the model install, the in-place
  model change with a real card, and the phone check are the rollout steps
  above.
- A companion older than 0.7.0 refuses to install the drill model
  (`BRIDGE_OPERATION_BODY_INVALID`); the bridge does not name the needed
  version in that error.
