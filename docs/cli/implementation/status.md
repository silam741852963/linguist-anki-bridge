# Implementation status

The implementation has started. The finalized handbook remains the target specification; this page records actual code coverage. No work package or release gate is complete yet.

`models install PURPOSE` now has a read-only CLI preview for all four built-in
purposes. It emits the exact v2 manifest and distinguishes absent names, byte
matching reuse candidates and same-name collisions. AnkiConnect does not prove
template order or managed provenance, so preview explicitly leaves installation
and apply eligibility false. `--apply` rejects before contacting Anki until the
native bridge, verified checkpoint and journal executor exist. Isolated CLI tests
cover missing/exact/colliding models and the write gate; no model was installed.

Vocabulary revamps now reuse verified Jisho/Wiktionary enrichment from authored
preparation. Explicit `auto`/`jisho` for Japanese and `auto`/`wiktionary` for English
save source revision 1 before dictionary lookup, then publish enriched revision 2.
Dictionary response bytes, all returned senses and dictionary evidence are retained;
original fields, source archives, tasks and meanings remain intact. Sense selection
remains an explicit review. Provider failure reports the retained source plan ID,
revision and digest; the original remains readable after restart.

`plans enrich PLAN --base-revision N --digest DIGEST` retries dictionary enrichment
from a retained draft using its frozen settings. It rejects stale bases, mismatched
digests, unsupported providers/grammar and already enriched plans. All lookups and
aggregate archive checks finish before publishing assets and the child revision;
publication uses the store's parent CAS. The child clears rendered/native binding
and carries no readiness or apply claim. A concurrent publication can leave
unreferenced immutable response assets, while the original revision is preserved.
Durable job workers still require `dictionary.provider=authored`; enrichment job
checkpoints are pending and requested enrichment is explicitly rejected.

Tests cover provider failure without advancing the plan, child publication and
restart, original Anki meaning/provenance/task preservation, sense review, saved
response bytes and stale/repeated enrichment rejection. No live provider or native
collection mutation is asserted by these tests.

Japanese dictionary review now supports `sense_with_reading` decisions for
multiple-reading entries. Review verifies the selected sense, expression and
exact written-form/reading pair before adopting facts. Existing `sense` decisions
retain their behavior. Validation binds the selected reading to the stored
review; even another valid reading needs a new decision. Tests cover ambiguous
readings, unrelated forms, invented/empty readings, typed JSON round-trip, durable
child publication and preserved parents. Schemas include the additive decision.

Revamp drafts now retain Production, Spelling and Application task candidates
when their explicitly mapped enable fields contain nonblank source values.
Markers such as `0` remain visible candidates rather than being silently treated
as Boolean false. Raw enable fields receive source evidence and
`SOURCE_TASK_MAPPING_REVIEW`; the native history issue remains unresolved.
Blank fields add no candidate. Shared/combined fields remain unresolved rather
than being guessed. Source cues/answers are retained, and missing cues remain
validation errors instead of removing tasks to render. Tests cover vocabulary and
grammar candidates, markers, blank fields, source preservation and cue failures.
This does not certify native card membership, ordinals or history preservation;
verified native task mapping and its typed review are still pending.

Dictionary card references now render entry forms/readings, provider/language,
source URL as inert text, numbered senses/labels, dictionary examples, metadata,
restrictions/relationships and related entries. Structured metadata appears in
collapsible sections; malformed metadata remains escaped text. The concise
selected answer stays ahead of the reference section. Provider text cannot
introduce active HTML, images or links. Tests cover facts/order and malicious
metadata, definitions, forms and URLs. Existing stored projections stay readable;
validation detects projections rendered by the older format as stale and requires
a newly rendered child before approval. No native template changes are made.

Grammar source splitting is now available through
`plans split-grammar PLAN --request FILE`. The version-2 request binds the exact
base revision/digest, source document/input digest, actor, ordered authored grammar
units and zero-based anchor index. It publishes a child with one original document
identity as anchor and fresh sibling IDs, preserving source archives and the
selection order. The explicit `grammar_groups` record is approval-bound and
validated against the exact archived request, including actor/anchor/unit count.
Empty groups are omitted so existing plan JSON/digests remain compatible.

Units require nonempty pattern/use keys and distinct pattern/use pairs; supplied
examples must be authored user examples. The anchor retains requested tasks;
siblings start with Recognition. Previous reviews and field edits are cleared;
source context/media/archives remain. Frozen input byte/character limits also bound
retained asset totals and the derived child size, with an early allocation estimate;
2–100 units is the current structural ceiling. Invalid/stale requests publish no
child. The exact request asset precedes plan publication and survives restart.
Concurrent conflicts can leave unreferenced immutable assets, never alter parents.
Native history/task mapping stays unresolved (`GRAMMAR_SPLIT_NATIVE_REVIEW`),
render/apply readiness is false, and no scheduling state is assigned to siblings.
Automatic screenshot segmentation, reviewed regrouping of existing groups, native
split execution and recovery/write ordering remain pending. Tests cover the Rust
boundary and CLI, invalid anchors, duplicate units, stale requests, forged group
metadata, source/parent preservation and restart recovery.

Typed cue/exercise repairs are now available through `plans resolve`.
Production/Spelling cues, missing Recognition prompts and complete Application
prompt/answer pairs are repaired only for matching requested tasks and issues.
They preserve tasks and source archives, clear corresponding overrides, invalidate
prior reviews and recompute validation/rendering in a new child. Empty content,
wrong-task repairs and answer leakage are rejected. Frozen record character limits
apply to repair content. Tests cover vocabulary and grammar, malformed repairs,
rendered enable flags, preserved parents/restart and readiness without apply
eligibility. Native task/history and generated/source fact reviews remain separate.

Interrupted source-read recovery is now available as
`jobs recover JOB [--after-index N] [--limit N]` (preview) or with
`--actor NAME --execute`. It inspects a bounded item page (1–1000, configured
page size by default) and returns a cursor; it makes no Anki requests. Execution
acquires the strong job-worker lease, re-reads the page and appends fenced
`interrupted` checkpoints for started items with the operator name and the same
attempt count. These items become retry candidates only within the frozen attempt
limit. `jobs run` performs any later dispatch separately. Captured/pending/failed
items, plans, assets and pause/cancel controls are preserved. Repeating recovery
without new started items appends nothing.

Expiry alone does not permit takeover: live or unverified owners remain blocked;
an absent expired owner can be fenced out. Checkpoint CAS/fencing is verified in
the append transaction. Tests cover missing recovery fencing, bounded retries,
preview/actor validation, expired-live rejection, simulated absent-owner recovery,
stale token rejection and idempotent repetition. This is read-only preparation
reconciliation, not recovery of unknown native mutation effects. No process-crash
or power-loss certification is claimed. The new interruption event variant uses
the current checkpoint schema; older binaries may reject it, so do not downgrade
an active store after recording recovery.

Focused plan inspection is now available through `plans show --item` and
`plans show --issues-only`. The issue view is bounded/paginated, revalidates the
exact saved revision, binds templates to the plan/document/issue digest and omits
raw archives. It shows supported sense/reading and typed cue/exercise choices,
source/generated evidence choices, and whether media decisions need manual
attributes. Templates are proposals only; the normal resolver rechecks every
submitted choice and requires a named actor. Unsupported issues are labelled
unavailable; no native verification or apply eligibility is inferred. Tests cover
pagination, disclosure boundary, exact fingerprints and CLI cue templates.

## Available foundation

- Root Rust workspace: `linguist-core`, `linguist-config`, `linguist-store`, `linguist-anki`, `linguist-application`, `linguist-dictionary` and `linguist-cli`; no Qt/Python runtime dependency.
- Typed vocabulary/grammar v2 documents, field intents, task definitions, rich dictionary/evidence/archive/media records, review decisions and initial plan/recovery records.
- Strict JSON parsing, RFC 8785 canonical bytes, domain-separated SHA-256 fingerprints; decimal-string Anki IDs.
- Fixed 18-field vocabulary and 15-field grammar model manifests and task templates.
- Offline semantic validation and rendering; escaping, reference sanitization, task prerequisite/leakage checks, generated-content review binding, source archive requirements and media manifest checks.
- Legacy v1 archive boundary preserves every JSON field; automatic v1 promotion and v2 downgrade are unavailable.
- Generated schemas under `contracts/v2/`; vocabulary/grammar examples.
- CLI development tools: `doctor`, `models`, `document validate`, `document render`, `document digest`. These are offline tools, not replacements for OP-21–OP-34 workflows. `ready` means domain validation passes; it is not permission or proof of collection apply readiness.

## Current limits and next work

WP-01 remains in progress: remaining native/resume/capability record contracts, prompt resources, dictionary rendering completeness and compatibility/schema coverage. Template card generation has not been verified in disposable Anki. UUID/hash/version constraints in generated schemas need parity validation beyond the typed JSON parser. A v1 archive is structurally preserved JSON, not a byte-identical copy or a verified restore snapshot.

WP-02 is in progress. The configuration crate embeds all 150 registry entries, validates typed values/ranges/maps and parses strict version-2 TOML. Resolution implements purpose presets, base/profile/purpose/env/flag precedence with provenance and a canonical effective-value fingerprint. It validates heartbeat/backoff/example/context constraints and rejects URL credentials and unapproved remote endpoints. The no-shell path expansion helper supports HOME/XDG tokens; consumers must freeze expanded paths when binding filesystem resources.

Available config commands: `init`, `show` (defaults/effective/provenance/key-prefix), `describe`, `validate`, `set`, `unset`, and `reset` (preview by default; `--execute` to save). Edits support explicit profile/purpose scopes, validate dormant profiles/purposes, preserve byte-exact private backups, lock cooperating editors, check prepublication file contents and atomically publish private TOML. Canonical serialization changes formatting; original comments remain in the backup. State relocation is blocked when the original state directory is nonempty or cannot be inspected. Initialization uses a synced private temporary file and no-replace publication. Document tools now consume registered input file/record limits. Help and builtin descriptions/defaults avoid configuration/service/state initialization. Config/schema diagnostics exit 2, unavailable capabilities exit 3, blocked rendering exits 4, ordinary I/O errors exit 6.

Still pending: full command graph, config import/migrate and init --replace, generated strict config schema, provider-specific template/parameter/resource capability validation, output formatting modes, frozen semantic/execution setting split, expanded-path freezing outside authored preparation and nondefault downstream consumption of every setting. Validation explicitly reports that runtime resources were not checked. No setting consumer coverage or WP-02 completion is claimed.

`completions SHELL` (OP-61) generates scripts directly from the current clap command schema for Bash, Elvish, Fish, PowerShell and Zsh. It runs before configuration resolution, never reads state/services and writes only script text to stdout. Unknown shells exit 2. Scripts include the currently implemented command graph; pending commands appear when their handlers are added. Generation uses a memory buffer so stdout failures follow the normal OUTPUT_IO diagnostic instead of panicking inside the generator. Tests cover all five shells with invalid configuration/settings, no state creation, no secret-option interpolation, unsupported shell rejection and Bash syntax. The dependency pair is pinned to [clap 4.6.7](https://docs.rs/clap/4.6.7/clap/) and [clap_complete 4.6.11](https://docs.rs/clap_complete/4.6.11/clap_complete/). No startup file is edited or completion script installed automatically.

WP-04 is in progress. The new store uses pinned rusqlite 0.40.2 with bundled SQLite, WAL, synchronous FULL and foreign keys. It checks private root/database paths and supported Linux filesystem types, publishes synced content-addressed assets before indexed metadata, validates immutable revisions and their exact parent digest, and verifies stored bytes when reading. Publication and reads both verify archive-only asset references and media manifest sizes; missing or corrupt original bytes prevent revision loading. Rendered output is recomputed before publication to reject stale projections. Initial schema creation and future-schema rejection are implemented; an interrupted initialization is reported rather than guessed away. `plans list`/`plans show` inspect revisions through a read-only connection; absent state is not initialized by listing. List currently reports revisions, without status filtering or pagination cursors. `plans diff PLAN --from-revision N [--revision M]` compares saved revisions and their exact approval digests, reports JSON-pointer changes with absent/null distinguished, and lists intended task additions/removals and captured card IDs. Arrays are compared as complete values. It never regenerates or writes state. Captured-source comparison and live conflict checks remain pending; `--live` explicitly reports unavailable capability. Task differences are intent, not verified card creation/deletion or native history preservation.

The store now has append-only journal events and compare-and-swap heads. Intent identities are immutable; unfinished requests and unverified observations are indexed for recovery, and later effects cannot start over an unresolved earlier step. Blind retry, sent-effect `failed_before_write`, and forged/stale prior versions are rejected. Terminal committed/compensated/restored writes remain unavailable until native/checkpoint/restore receipts exist. `recover inspect OPERATION` or `recover inspect --pending` reads local evidence only; `--live` explicitly reports unavailable capability.

Durable job-worker and bridge-writer leases use unique tokens and generations. Linux boot ID + PID + process start ticks distinguish worker identity from PID reuse. Expiry alone cannot reclaim a live/unverifiable owner; renewal/release reject stale tokens, and nested helpers must borrow an existing token. Lease enforcement has not yet been connected to any application dispatch or native adapter.

Store schema 5 contains journals, leases, append-only validation evidence and immutable approval records. Ordered v1/v2/v3/v4 upgrades first create a private SQLite online backup, switch that backup to standalone DELETE journal mode, sync it and check integrity before the transactional schema upgrade. Future versions remain rejected. Tests include a separate process exiting immediately after durable `request_started`; reopening preserves the pending record. This verifies that local boundary only, not an Anki-side effect or arbitrary power loss.

WP-04 remains incomplete: verified native receipt/checkpoint transitions, adapter-level lease enforcement and unknown-effect blocking, complete disk-full/crash boundary injection, startup orphan cleanup, source/archive relationship and indexed-reference graph verification and free-space reserve enforcement. Filesystem checks are a prerequisite, not proof against arbitrary backing mounts or power-loss behavior. Temporary-file cleanup is best effort and pruning is not implemented.

WP-03 is in progress. A sealed read-only AnkiConnect port exposes version/reflection/profile, decks/models/field-template-CSS manifests, note/card queries and bounded info calls. It consumes endpoint/credential-reference/profile/timeout/batch/response/network policy settings. HTTP redirects, automatic retries and inherited proxies are disabled; configured proxy support returns explicit unavailable capability. Loopback works offline. Remote hosts require opt-in and public resolved addresses; bounded DNS resolution pins addresses for the client. API envelope duplicate keys/unsafe numbers, response overflow, profile drift and info ID/count mismatches are rejected. Error messages do not echo server payloads or credentials.

CLI reads now include `doctor` (`--local` skips probes; `--offline` permits loopback only), `decks list/show`, `models list/inspect/builtin`, and `notes list/show/count`. Note summaries omit fields. List cursors bind the query and observed ID set; drift invalidates the cursor. Deck counts explicitly include subdecks. Numeric v6 API IDs are converted to decimal strings for output; IDs outside the v6 safe numeric range fail rather than being coerced. Plain AnkiConnect does not expose trustworthy template order or complete native history/home-deck identity, so managed verification stays false and binding confidence stays weak.

Read-only live smoke probes succeeded against the installed add-on; see [read-port evidence](../evidence/read-port-2026-09-26.md). The bridge was absent. These probes and HTTP fixture tests do not pass any native mutation release gate.

WP-03 remains incomplete: companion add-on/protocol, strong binding, native dedupe/CAS/authentication, disposable-collection migration/history/backup/restore proofs. Read command completion also needs full deck/model filters and pagination, field/media reference parsing, home-deck/history capture, service-wide deadlines/retry budgets, exhaustive output-mode coverage and provider/model/resource doctor checks. Count calls are separate native reads, not an atomic collection snapshot; profile checks cannot detect same-profile collection replacement.

`models inspect MODEL` now includes structured compatibility reports against both fixed v2 manifests. Reports retain target field order, every exact-name source ordinal, missing/unexpected fields and duplicate source names; no aliases or combined legacy fields are inferred. Template reports distinguish absent templates and front/back differences, expose unexpected template names, and compare CSS separately. Renamed but byte-matching content is distinguished from a matching managed name. Source task/template ordinals remain unverified, and neither content matching nor a model name grants managed status or apply authorization. WP-05 source-media discovery has started. A pure application helper parses bounded raw fields using [scraper 0.27.0](https://docs.rs/scraper/0.27.0/scraper/) HTML parsing plus Anki sound-marker syntax. It preserves repeated references and field associations, decodes HTML entities through the parser and percent-decodes HTML URL filenames exactly once; sound filenames remain literal. Images, audio/video/source/embed/object references and video posters are recognized. Unsafe/remote/path references, invalid UTF-8 escapes, incomplete sound markers, case collisions and unsupported CSS/srcset/embedded media syntax become explicit discovery issues. No URL is fetched or source field rewritten. Total input bytes and discovered references/issues are bounded, with fixed safety ceilings of 100 MiB and 10,000 observations. `notes show` now includes `parsed_media`, consumes configured input limits and retains original field JSON. An isolated Anki fixture verifies raw preservation, local/remote distinction, read-only action calls and no state initialization. Opt-in media retrieval is implemented as described below. Media format validation, archive publication, complete CSS/srcset handling and native history capture remain pending; default inspection does not read media bytes. This discovery helper does not establish a complete revamp capture or authorize transformation.

`notes show NOTE_ID --media` retrieves each distinct safe discovered filename through the read-only Anki adapter, with profile checks before and after every read. The installed AnkiConnect implementation was inspected: `retrieveMediaFile` returns Base64 or `false`, and normalizes/strips filename characters. The adapter rejects unsafe paths/remote URLs, non-NFC names, wildcard/pipe names and trailing dot/space instead of silently requesting a changed file. NFC validation uses [unicode-normalization 0.1.25](https://docs.rs/unicode-normalization/0.1.25/unicode_normalization/fn.is_nfc.html). False is missing, while null/true/non-string results are protocol errors. Strict padded Base64 and decoded-size preflight enforce `media.max_asset_mb` before payload allocation; the independent network response limit remains in force. Original bytes receive a SHA-256 digest. CLI output contains hashes/sizes/existence, never payload bytes; bytes are not retained or written to local state by inspection. `media_inspection_requested` distinguishes the option, and `media_bytes_checked` is true only when discovery has no issues and every reference exists. This is not image/audio decoding proof: `media_content_validated=false` remains explicit. Missing files are reported rather than replaced. Four adapter tests and an isolated CLI fixture cover exact bytes, nondefault limits, missing files, malformed Base64, unsafe names, profile drift, read-only calls and no state writes. The read remains weak identity evidence; same-profile collection replacement and native history are not verified.

WP-09 has started with typed patch editing: `plans edit PLAN --base-revision N --patch FILE [--save-draft]`. The version-2 patch binds the exact parent approval digest and document IDs. Changed item reviews and plan-level decisions are invalidated conservatively. Validation/rendering is rerun; review-needed or invalid children require explicit `--save-draft`, contain issues, and omit blocked renders. Empty/no-op patches retain the existing revision. No editor or provider is launched. Editor mode, typed identity/task/media branches, dependency-specific review invalidation and the other WP-09 operations remain pending.

WP-05/WP-07/WP-08 have started with `vocab add --document FILE` and `grammar add --document FILE` for one authored v2 JSON record. The envelope has `schema_version`, `kind`, `target_language`, optional `explanation_language`, typed `body`, and optional context/personal notes/tags/tasks. Omitted tasks use registered new-note settings; explicit tasks win. Input body/record limits and strict JSON apply. Exact UTF-8 bytes are stored as a content-addressed archive before immutable plan publication. Frozen settings expand path-format values to absolute paths and recompute the fingerprint; API credentials remain environment names, with no secret values stored. Content errors are retained in the plan for inspection; invalid items have no rendered output. Output distinguishes content readiness from apply eligibility and explicitly reports duplicate checking as unperformed.

Structured add commands now accept `--document -` for one piped or redirected UTF-8 JSON record. The shared JSON reader also accepts `-` for document tools and typed patch/decision input files. It reads at most the configured body limit plus one byte, applies the character limit and rejects malformed encoding or multiple JSON values before state initialization. Interactive terminal input is rejected with a pipe/redirection instruction rather than waiting for manual EOF. Input whitespace and trailing newline bytes remain in the original archive and digest; stdin is not split into inferred rows. Tests verify byte-exact archive retrieval, normal digest tooling and invalid encoding, record/body limits and multiple-value rejection without state creation. JSONL/CSV and plain inline text remain pending explicit modes.

This initial path requires `llm.enabled=false`, `dictionary.provider=authored`, no active image search, and audio preserve/disabled. Applicable Japanese kanji enrichment must be disabled until implemented. Requested unavailable providers fail before state initialization. Structured sources/media/evidence import, inline/file/JSONL/CSV inputs, duplicate reads, deck intents, source selectors/revamp and provider enrichment remain pending. `plans validate PLAN [--revision N]` recomputes domain readiness and staged-render consistency, checks all referenced asset bytes through revision loading, and persists append-only evidence linked to the exact approval digest. Store reads recheck evidence hashes, plan links and recomputed readiness; callers cannot supply a ready boolean. Validation never changes plan content or grants apply eligibility. `--live` reports unavailable native conflict inspection. SQL triggers reject updates/deletes of reports. Schema-3 upgrade tests verify a standalone pre-upgrade backup and retained revisions/lease table. Validation schema generation is included in the core schema example.

`plans approve PLAN --revision N --digest DIGEST --actor ACTOR [--item-id UUID] [--accept-warning CODE]` records immutable local content approval. Selected items must validate and match staged renders; accepted warnings must exactly cover known warning codes, with no error/review waiver. Unknown/duplicate item IDs and warning codes fail. Latest-revision/digest checks run in the publication transaction, so concurrent edits cannot approve stale content. Empty selection is a no-op. Historical approvals remain inspectable through the store without becoming current write authorization. Approval receipts explicitly return `apply_authorized=false`; timestamps are recorded as `unix-seconds:N`, and actor names are explicit, bounded and control-free. Schema-4 migration preserves prior validation evidence with a pre-upgrade backup. Approval request schema is generated from the core type.

`plans resolve PLAN ISSUE --decision FILE` supports typed generated-fact content verification. The v2 decision request includes base revision/digest, document ID, issue ID, current semantic input digest, actor and `content_verified` evidence IDs. Only currently unresolved review issues can resolve; error/warning waivers fail. Exact, unique evidence references are required. The decision is recorded on the document and child plan, validation/rendering is recomputed without provider calls, and publication checks immutable parent history. Remaining unresolved content returns exit 4. Dictionary sense decisions are implemented as described below; remaining decision kinds explicitly report unavailable capability until their pipeline branches are implemented. Resolution request schema is generated from the core type.

`plans export PLAN --output FILE [--revision N] [--include-private-archives]` creates a private, no-overwrite JSON inspection bundle. The default contains staged rendered card content and selected non-archive media; card content can itself be private. Explicit archive inclusion adds the complete typed revision and original archived bytes. The manifest labels disclosure scope and records the original plan digest, asset SHA-256/size metadata, fixed Base64 encoding and a domain-separated manifest digest; the receipt supplies the complete file checksum. Assets stream one at a time, so total bundle size does not require keeping all asset bodies in memory. Publication syncs a private temporary file, uses no-replace hard-link publication and syncs the output directory. Existing destinations remain untouched; postpublication directory-sync failure explicitly reports uncertain durability. Parent directories must already exist. Secret environment values are never fetched. V1 and unsupported formats fail. Import/apply authorization and replacement-with-backup remain unavailable; this bundle is not an Anki backup or restore checkpoint. Export schema generation is included in the application example. Base64 encoding follows the [pinned crate API](https://docs.rs/base64/0.23.1/base64/).

WP-06 has started with a pure Jisho API-v1 response parser in `linguist-dictionary`. It bounds response bytes/result counts, rejects duplicate JSON keys/unsafe numbers/schema failures, requires Japanese target language and explicit provider success, and treats an empty result as ordinary dictionary-not-found. Entries remain in provider order; exact-match indexes are evidence, never automatic selection. All written form/reading associations, English definition-language metadata, sense labels/restrictions/info/related words, provider extensions and original response bytes/digest are preserved. Sense keys bind the slug and complete sense data. Search queries and word links use URL encoding and a fixed Jisho origin; external text remains data. Synthetic compatibility fixtures were derived from the archived Rust/Python parser shapes. The live API response was not verified: the research browser could not open it. A shared fixed-origin Jisho/Wiktionary HTTP client now pins bounded DNS results to public addresses, uses TLS, disables inherited proxies and reqwest retries, and bounds response MIME/body/redirects. Only same-origin redirects are followed. Queue/rate waits, reads, response bodies and backoff share a lookup deadline. Classified transient read failures retry with bounded randomized exponential backoff and Retry-After in seconds or HTTP-date form; auth/schema/content-policy failures do not retry. All clients for the same fixed origin share a process-wide serialized lookup/rate gate, including separately constructed clients. The two supported origins remain independent. Gate history survives dropping clients; adjacent dispatches respect both the prior and current minimum interval. Server Retry-After cooldowns survive exhausted attempts and deadline refusal, so a subsequent client cannot immediately bypass them. Huge valid delays are tracked as elapsed durations without overflowing monotonic timestamps. Queue/rate/cooldown waits remain within each lookup deadline. Policy-checked proxies and configured concurrency above one explicitly fail rather than being ignored. Retry-After also applies to same-origin redirects, never bypasses the total deadline, rejects multiple/malformed values and maps past dates to zero server delay. Date parsing uses pinned httpdate 1.0.3; subsequent waits use the monotonic deadline. Cross-process coordination, cancellation, worker-bounded DNS, cache, provider CLI commands and completion of dictionary preparation remain pending. No live Jisho request was run as validation; tests use isolated localhost fixtures. Authored mode skips lookup; vocabulary preparation uses this client for Japanese jisho/auto and English wiktionary/auto.

Japanese vocabulary preparation can now use `dictionary.provider=jisho` or `auto`. The structured vocabulary input permits omitted meaning/sense key for lookup, while final documents retain their strict readiness requirements. The response is reparsed at the application boundary to bind rich facts to exact saved bytes. All entries/senses, dictionary evidence and full raw-response archives are published with the plan. Dictionary-not-found preserves authored facts and adds an explicit warning. No sense is silently chosen: `plans resolve` accepts a typed `sense` choice for `DICTIONARY_SENSE_REVIEW`, requires an exact expression match and matching written-form reading, sets dictionary-owned meaning/key/reading, invalidates prior content-bound decisions, and binds the new decision to the resulting semantic document. Generic field edits cannot override active dictionary facts. Non-English definition explanations and ambiguous reading-selection branches remain explicitly unavailable. Other active enrichments still require their documented disabled/preserve settings. Preparation output now supplies document ID and semantic input digest for decision construction. Fake-port tests verify archive bytes, all-sense retention, explicit selection to readiness, stale-decision invalidation and rejection of facts not represented by raw provider data; live Jisho integration evidence remains pending.

The English dictionary parser now supports a versioned Wiktionary definition-response shape. It validates language-section maps and English section labels, retains POS/sense/example/extension data and original multilingual response bytes, and creates stable sense keys. HTML-derived plain text preserves block boundaries and decodes entities with pinned html-escape 0.2.15; script/style content and attributes are discarded from the derived display while original HTML remains archived. Tests cover this distinction, including regional English tags and the mandatory sentence requirement. Live endpoint compatibility remains pending; HTTP 404 currently reports a provider error rather than dictionary-not-found.
