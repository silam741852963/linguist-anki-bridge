# Implementation status

The implementation has started. The finalized handbook remains the target specification; this page records actual code coverage. No work package or release gate is complete yet.

## Available foundation

- Root Rust workspace: `linguist-core`, `linguist-config`, `linguist-store`, `linguist-anki`, `linguist-application`, `linguist-dictionary` and `linguist-cli`; no Qt/Python runtime dependency.
- Typed vocabulary/grammar v2 documents, field intents, task definitions, rich dictionary/evidence/archive/media records, review decisions and initial plan/recovery records.
- Strict JSON parsing, RFC 8785 canonical bytes, domain-separated SHA-256 fingerprints; decimal-string Anki IDs.
- Fixed 18-field vocabulary and 15-field grammar model manifests and task templates.
- Offline semantic validation and rendering; escaping, reference sanitization, task prerequisite/leakage checks, generated-content review binding, source archive requirements and media manifest checks.
- Legacy v1 archive boundary preserves every JSON field; automatic v1 promotion and v2 downgrade are unavailable.
- Generated schemas under `contracts/v2/`; vocabulary/grammar examples.
- CLI development tools: `doctor`, `models`, `document validate`, `document render`, `document digest`. These are offline tools, not replacements for OP-21–OP-34 workflows. `ready` means domain validation passes; it is not permission or proof of collection apply readiness.

## Current limits and next work

WP-01 remains in progress: remaining native/resume/capability record contracts, prompt resources, dictionary rendering completeness and compatibility/schema coverage. Template card generation has not been verified in disposable Anki. UUID/hash/version constraints in generated schemas need parity validation beyond the typed JSON parser. A v1 archive is structurally preserved JSON, not a byte-identical copy or a verified restore snapshot.

WP-02 is in progress. The configuration crate embeds all 150 registry entries, validates typed values/ranges/maps and parses strict version-2 TOML. Resolution implements purpose presets, base/profile/purpose/env/flag precedence with provenance and a canonical effective-value fingerprint. It validates heartbeat/backoff/example/context constraints and rejects URL credentials and unapproved remote endpoints. The no-shell path expansion helper supports HOME/XDG tokens; consumers must freeze expanded paths when binding filesystem resources.

Available config commands: `init`, `show` (defaults/effective/provenance/key-prefix), `describe`, `validate`, `set`, `unset`, and `reset` (preview by default; `--execute` to save). Edits support explicit profile/purpose scopes, validate dormant profiles/purposes, preserve byte-exact private backups, lock cooperating editors, check prepublication file contents and atomically publish private TOML. Canonical serialization changes formatting; original comments remain in the backup. State relocation is blocked when the original state directory is nonempty or cannot be inspected. Initialization uses a synced private temporary file and no-replace publication. Document tools now consume registered input file/record limits. Help and builtin descriptions/defaults avoid configuration/service/state initialization. Config/schema diagnostics exit 2, unavailable capabilities exit 3, blocked rendering exits 4, ordinary I/O errors exit 6.

Still pending: full command graph, config import/migrate and init --replace, generated strict config schema, provider-specific template/parameter/resource capability validation, output formatting modes, frozen semantic/execution setting split, expanded-path freezing outside authored preparation and nondefault downstream consumption of every setting. Validation explicitly reports that runtime resources were not checked. No setting consumer coverage or WP-02 completion is claimed.

`completions SHELL` (OP-61) generates scripts directly from the current clap command schema for Bash, Elvish, Fish, PowerShell and Zsh. It runs before configuration resolution, never reads state/services and writes only script text to stdout. Unknown shells exit 2. Scripts include the currently implemented command graph; pending commands appear when their handlers are added. Generation uses a memory buffer so stdout failures follow the normal OUTPUT_IO diagnostic instead of panicking inside the generator. Tests cover all five shells with invalid configuration/settings, no state creation, no secret-option interpolation, unsupported shell rejection and Bash syntax. The dependency pair is pinned to [clap 4.6.7](https://docs.rs/clap/4.6.7/clap/) and [clap_complete 4.6.11](https://docs.rs/clap_complete/4.6.11/clap_complete/). No startup file is edited or completion script installed automatically.

WP-04 is in progress. The new store uses pinned rusqlite 0.40.2 with bundled SQLite, WAL, synchronous FULL and foreign keys. It checks private root/database paths and supported Linux filesystem types, publishes synced content-addressed assets before indexed metadata, validates immutable revisions and their exact parent digest, and verifies stored bytes when reading. Publication and reads both verify archive-only asset references and media manifest sizes; missing or corrupt original bytes prevent revision loading. Rendered output is recomputed before publication to reject stale projections. Initial schema creation and future-schema rejection are implemented; an interrupted initialization is reported rather than guessed away. `plans list`/`plans show` inspect revisions through a read-only connection; absent state is not initialized by listing. List currently reports revisions, without status filtering or pagination cursors. `plans diff PLAN --from-revision N [--revision M]` compares saved revisions and their exact approval digests, reports JSON-pointer changes with absent/null distinguished, and lists intended task additions/removals and captured card IDs. Arrays are compared as complete values. It never regenerates or writes state. Captured-source comparison and live conflict checks remain pending; `--live` explicitly reports unavailable capability. Task differences are intent, not verified card creation/deletion or native history preservation.

The store now has append-only journal events and compare-and-swap heads. Intent identities are immutable; unfinished requests and unverified observations are indexed for recovery, and later effects cannot start over an unresolved earlier step. Blind retry, sent-effect `failed_before_write`, and forged/stale prior versions are rejected. Terminal committed/compensated/restored writes remain unavailable until native/checkpoint/restore receipts exist. `recover inspect OPERATION` or `recover inspect --pending` reads local evidence only; `--live` explicitly reports unavailable capability.

Durable job-worker and bridge-writer leases use unique tokens and generations. Linux boot ID + PID + process start ticks distinguish worker identity from PID reuse. Expiry alone cannot reclaim a live/unverifiable owner; renewal/release reject stale tokens, and nested helpers must borrow an existing token. Lease enforcement has not yet been connected to any application dispatch or native adapter.

Store schema 5 contains journals, leases, append-only validation evidence and immutable approval records. Ordered v1/v2/v3/v4 upgrades first create a private SQLite online backup, switch that backup to standalone DELETE journal mode, sync it and check integrity before the transactional schema upgrade. Future versions remain rejected. Tests include a separate process exiting immediately after durable `request_started`; reopening preserves the pending record. This verifies that local boundary only, not an Anki-side effect or arbitrary power loss.

WP-04 remains incomplete: verified native receipt/checkpoint transitions, adapter-level lease enforcement and unknown-effect blocking, complete disk-full/crash boundary injection, startup orphan cleanup, source/archive relationship and indexed-reference graph verification and free-space reserve enforcement. Filesystem checks are a prerequisite, not proof against arbitrary backing mounts or power-loss behavior. Temporary-file cleanup is best effort and pruning is not implemented.

WP-05 source-media discovery has started. A pure application helper parses bounded raw fields using [scraper 0.27.0](https://docs.rs/scraper/0.27.0/scraper/) HTML parsing plus Anki sound-marker syntax. It preserves repeated references and field associations, decodes HTML entities through the parser and percent-decodes HTML URL filenames exactly once; sound filenames remain literal. Images, audio/video/source/embed/object references and video posters are recognized. Unsafe/remote/path references, invalid UTF-8 escapes, incomplete sound markers, case collisions and unsupported CSS/srcset/embedded media syntax become explicit discovery issues. No URL is fetched or source field rewritten. Total input bytes and discovered references/issues are bounded, with fixed safety ceilings of 100 MiB and 10,000 observations. `notes show` now includes `parsed_media`, consumes configured input limits and retains original field JSON. An isolated Anki fixture verifies raw preservation, local/remote distinction, read-only action calls and no state initialization. Opt-in media retrieval is implemented as described below. Media format validation, archive publication, complete CSS/srcset handling and native history capture remain pending; default inspection does not read media bytes. This discovery helper does not establish a complete revamp capture or authorize transformation.

`notes show NOTE_ID --media` retrieves each distinct safe discovered filename through the read-only Anki adapter, with profile checks before and after every read. The installed AnkiConnect implementation was inspected: `retrieveMediaFile` returns Base64 or `false`, and normalizes/strips filename characters. The adapter rejects unsafe paths/remote URLs, non-NFC names, wildcard/pipe names and trailing dot/space instead of silently requesting a changed file. NFC validation uses [unicode-normalization 0.1.25](https://docs.rs/unicode-normalization/0.1.25/unicode_normalization/fn.is_nfc.html). False is missing, while null/true/non-string results are protocol errors. Strict padded Base64 and decoded-size preflight enforce `media.max_asset_mb` before payload allocation; the independent network response limit remains in force. Original bytes receive a SHA-256 digest. CLI output contains hashes/sizes/existence, never payload bytes; bytes are not retained or written to local state by inspection. `media_inspection_requested` distinguishes the option, and `media_bytes_checked` is true only when discovery has no issues and every reference exists. This is not image/audio decoding proof: `media_content_validated=false` remains explicit. Missing files are reported rather than replaced. Four adapter tests and an isolated CLI fixture cover exact bytes, nondefault limits, missing files, malformed Base64, unsafe names, profile drift, read-only calls and no state writes. The read remains weak identity evidence; same-profile collection replacement and native history are not verified.

`plans validate PLAN [--revision N]` recomputes domain readiness and staged-render consistency, checks all referenced asset bytes through revision loading, and persists append-only evidence linked to the exact approval digest. `plans approve PLAN --revision N --digest DIGEST --actor ACTOR [--item-id UUID] [--accept-warning CODE]` records immutable local content approval. `plans resolve PLAN ISSUE --decision FILE` supports typed generated-fact content verification. The v2 decision request includes base revision/digest, document ID, issue ID, current semantic input digest, actor and `content_verified` evidence IDs. Only currently unresolved review issues can resolve; error/warning waivers fail. Exact, unique evidence references are required. `plans export PLAN --output FILE [--revision N] [--include-private-archives]` creates a private, no-overwrite JSON inspection bundle. Assets stream one at a time, so total bundle size does not require keeping all asset bodies in memory. Publication syncs a private temporary file, uses no-replace hard-link publication and syncs the output directory. Existing destinations remain untouched; postpublication directory-sync failure explicitly reports uncertain durability. Parent directories must already exist. Import/apply authorization and replacement-with-backup remain unavailable; this bundle is not an Anki backup or restore checkpoint. Export schema generation is included in the application example.
