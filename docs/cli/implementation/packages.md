### Storage evidence (2026-10-03)

The root `linguist-store` now uses schema 8. The new snapshot tables retain immutable original bodies and asset references separately from one native after-state receipt and actual after-state asset. Publication verifies every archived asset and media size before committing a snapshot. Reads verify body hashes, the reference index and archived bytes. A structural native receipt with a read-back and archived evidence can be attached once only when its step ID, payload, approval, lineage, session and observed digest match the linked started journal step. The actual after-state bytes must already be archived under that observed digest. This local record does not finalize a journal or authorize a native write. Schema 7 upgrades create a checked private SQLite backup before adding the tables.

`snapshots list` and `snapshots show` now read this evidence without creating state. List pages by UUID and supports exact source note, journal job and recorded/unknown post-state filters; a cursor advances by scanned records even when the filter excludes them. Restore/export remain later-package work. Store tests exercise restart, a process killed between publishing asset bytes and metadata, file-size-limit write failure, transactional index failure, missing/corrupt assets, immutable history and schema-7 backup. Existing store tests cover journal unknown-state restart and no unverified finalization, lease contention/reclaim and future-schema refusal.

### Known limits — revisit after all packages

These gaps were left open deliberately and must be closed or re-accepted after WP-16.

- Piper was tested only against a fake executable; no Piper binary or voice was available. Voice license evidence is limited to hashing the model and its config; no license file is checked.
- The Jisho kanji parser and the Commons response handling were each checked against one live response; the fixtures are reduced copies. Upstream markup or API changes fail as `PROVIDER_READ_Schema`; they are not detected ahead of time.
- PaddleOCR, Ollama vision OCR, `classification.vision_adjudication`, the browser helper (`browser.*`, `dictionary.browser_fallback`), custom dictionary/image/audio endpoints, dictionary audio and `network.proxy_env` return explicit unavailable errors and are not implemented.
- Image classification is an uncalibrated layout heuristic (`ocr-layout-heuristic-v1`); the legacy logistic model and user-feedback calibration were not ported.
- OCR reads only the first frame of animated images. Tesseract confidence is engine-specific and uncalibrated.
- Helper sandboxing covers only: no shell, a cleared environment, its own process group, the `RLIMIT_AS` address-space limit, the deadline and the output bound. There is no seccomp, namespace, cgroup or filesystem confinement, so a helper can read anything the user can read. A grandchild that calls `setsid` can escape the group kill. Between reaping the leader and the group kill there is a small PID-reuse window.
- `doctor --local` runs the configured OCR executable (`--version`, `--list-langs`) to probe it.
- OCR runs only during revamp capture under `images.existing_policy=inspect`; authored add has no image input.
- Rate gates and service semaphores are per process; concurrent CLI processes do not coordinate. Ollama keeps its own loopback-only transport with concurrency 1 rather than the shared reader.
- The provider and OCR caches are never pruned or size-limited: `cache.max_size_mb` and `cache.unreferenced_retention_days` are unconsumed until WP-14. TTLs use wall-clock time. A cache write failure is silent.
- Each DNS lookup uses one thread; the public-address check follows fixed IPv4 special ranges and IPv6 `2000::/3` minus documentation space, not the full IANA registry.
- Manual OCR transcription (editing region text) is WP-09 work. Choosing an expression from OCR text accepts only one single-line region of at most 200 characters.

### Known limits — revisit after all packages

- Kanji, picture and audio enrichment inside preparation was tested with fake ports only; there is no live end-to-end run.
- Image search uses the expression alone and runs before sense selection. Candidate relevance therefore depends on reviewer judgement; nothing is sense-aware.
- Audio is synthesized from the reading when present, otherwise the expression. In the dictionary flow the reading is empty before sense review, so a Japanese kanji expression is spoken from kanji and may be mispronounced; review is required anyway.
- Kanji enrichment covers Japanese with English explanations only. It is all-or-nothing on provider failure, skips characters with no details, and stores the full kanji page HTML in the plan's source fields, which grows plan size.
- Declined media candidates and kanji pages stay in the content store with no pruning (WP-14).
- `plans enrich` re-runs only dictionary lookup. Kanji/picture/audio enrichment cannot be retried on demand, and any stored enrichment-stage issue stops a revamp from enriching again.
- Duplicate decisions are recorded intent only. Apply does not enforce them yet (WP-11); collection duplicate checking stays incomplete. `--record` requires a rendered authored item, because inspection does.
- Cue suggestions are templates: production uses the meaning; spelling uses the kana reading, then the pronunciation, then the meaning. A reviewer must still submit them.
- Inline generation runs sequentially, one revision per item, with no retry. Generated items stay not-ready because of `GENERATION_ENGINE_UNVERIFIED`. With `llm.enabled=true`, add/revamp always exit 4.
- Typed cue/media/duplicate/segmentation decisions rebind earlier sense/media/duplicate/segmentation decisions that still validate; every other edit reopens all decisions. Validation-stage issues are always recomputed and are never stored input.

Read capture records no cards, so card task and deck drift since preparation is not detected unless cards were captured. Source media bytes are not compared (capture does not archive media hashes). Anki's case-insensitive tag semantics are not modelled; tags are compared exactly.
- Cross-language canonicalization is proven for one precondition vector only. The companion's `jcs` is `json.dumps` with sorted keys, which differs from RFC 8785 for keys outside the Basic Multilingual Plane and for floats (neither is used today).
- Tags are only added. Planned tag removal is not represented in documents, so it cannot be applied.
- Deck mapping is per note, not per card or task. Every card moves to the purpose's target deck, or to the single existing home deck when no target is configured; several home decks without a target fail `APPLY_DECK_MAPPING_AMBIGUOUS`. A reviewed per-task deck map does not exist.
- Card generation is inferred. The desired cards come from rendered task ordinals. If Anki's template-emptiness rules generate a different set, the read-back mismatches and the item needs recovery; it is not reported as a success, but it is also not prevented in preflight.
- Study during the mutation window is not distinguished from migration damage. Any scheduler or history change between the fresh capture and the read-back enters `needs_recovery`. There is no rule that accepts append-only study after the native receipt, and no operator path to accept it.
- Migration limits: only an explicit `SourceTaskMap` is accepted; every source card must be mapped; there is no scoped destructive decision for dropping a task. The native migration maps no fields and then writes all managed fields, so source-only field content survives only in the snapshot archive. Reverse migration and restore are WP-12. `--accept-schema-change` exists on the CLI but is not consumed, because apply is gated, and no full-sync warning text is shown.
- Grammar split groups (ALG-SPLIT) are blocked with `CAPABILITY_UNAVAILABLE` (WP-12).
- Checkpoints are not created by apply. The caller must supply an existing verified receipt ID, and WP-10's limits apply (no live export, whole-collection packages, presence and lower-bound scope checks). New media names are not part of the checkpoint scope. No recovery group is built across items; `group_id` is passed through.
- Leases and owners: as in WP-10, the store lease token is validated but not proven to be the collection-writer lease for the bound lineage. The fake port only counts owner tokens; fencing, owner expiry and stale fenced requests are untested. The owner is released after accounting even when an effect is unresolved; companion behavior for that case is untested. Reconciliation without `--apply` takes no owner.
- Local durability windows remain. The intent record, the snapshot and the first journal version are separate SQLite transactions: a crash between them leaves an intent or snapshot with no journal. It is treated as never dispatched, but `recover inspect` does not list it. "Disk full" is simulated with a held SQLite write lock, not a real `ENOSPC` or fsync failure.
- Known partials stay pending. An operation with verified media and a native refusal of the note step remains `needs_recovery` in `recover inspect --pending` even after a new attempt supersedes it; there is no terminal "superseded" state. Uploaded media is never deleted.
- Resubmission safety depends on companion deduplication of the same UUID and payload. The ledger implements that only for queued `create_note` intents and has no live dispatcher.
- Review outcomes have no operator workflow. When reconciliation reports `review`, there is no command to adopt a differing state, record an observed-state-bound choice or export evidence; restore is WP-12. Only rebinding decisions are recorded.
- Rebinding is library-only. The CLI `--rebind` flag cannot construct a `ResumeBindingDecision` (no actor or evidence input), and live rebind is gated with the rest of reconciliation.
- CLI scope: the `apply` preview is local only. It does not check live identity, model, deck, media or source state, and reports `update_or_migrate` without resolving it. `recover reconcile` without `--apply` shows a local proposal, not the live matched/absent/partial/conflict evidence that OP-60 step 2 describes. Checkpoint and model journals report `unsupported_journal_kind`; model reconciliation still has no CLI.
- Batches are library-only. `apply_items` classifies stop conditions by error-code prefix. No CLI or job runs batches, and plan status (`applying`, `applied`, `partial`) is not recorded on plan revisions (WP-13).
- Settings are not consumed by apply: `anki.request_timeout_seconds` and `anki.commit_interval_seconds` (the mutation deadline belongs to the future adapter), `media.max_asset_mb` (the caller passes `max_media_bytes`) and `backup.reuse_max_age_seconds` (not passed by any CLI path).
- The receipt is application-built. The verified `NativeOperationReceipt` is constructed from the CLI's own read-back, not received from the companion ledger. Its evidence digest names the local read-back asset, and its history digest covers retained cards only.
- Identity checks: loopback is judged from the endpoint URL host only, with no same-host artifact accessibility check. `capability_digest` is not compared between the approval and execution bindings.
- Approval scope: any stored approval that covers the item is accepted. Approving a ready revision within the apply invocation (ALG-APPLY step 1 alternative) is not implemented. Duplicate decisions are not rechecked at apply beyond plan-validation readiness. Media MIME and role are not rechecked at apply.
- Evidence breadth: one Anki build (25.09.2) and one disposable collection, vocabulary only (no grammar apply), a synthetic Basic source (not the real Picture Words model), no AnkiConnect, no concurrent UI edits, no real process-kill crash injection. The failure-matrix rows for split children, restore, concurrent apply/restore and cache pruning belong to WP-12–WP-14 and are not covered here.

## Package WP-12 — restore/splits

Source: [wp-12.md](wp-12.md)

Touch: existing application restore orchestration, snapshots/group journals. Read ALG-SPLIT, ALG-RESTORE and OP-44, OP-50.

Steps: child stable IDs/anchor ordering, known partial recovery, separate restore intent/checkpoint/current snapshot, media-before-reference order, conflict-aware content merge, retained later study preservation, explicit created-note/task loss review. Avoid deletion of shared schema/source media.

Tests: child accepted/anchor failed, repeated resume no duplicates, every reverse effect crash boundary, later personal edit/review, studied child protection, reverse mapping incompatibility, unchanged original receipt and source archive. Done when grouped operation can safely resume or report exact unsupported recovery instead of claiming rollback success.

### Completion audit — 2026-10-04

- Restore (ALG-RESTORE, OP-50): `linguist_application::restore::plan_restore` is the live preview. It loads the snapshot, the frozen apply intent and its journal, checks collection identity and loopback, and reads the current note, media and models. It reports a field, tag, model, per-card deck, card and media diff with the history consequences, the conflicts that need a decision, and the blockers that make recovery unsupported. `restore::restore` needs the current invocation's `--apply`, the store lease, and a `RestoreDecision` whose `observed_state_digest` equals the preview. There is no force flag: each conflict needs its own field choice (`original`, `current` or reviewed `merged` text), deck choice, card-removal entry, missing-media acceptance or schema-change acceptance.
- Targets: only snapshots of apply operations can be restored. Imported, split-source and restore snapshots return `RESTORE_TARGET_UNSUPPORTED` (inspect/export only). The target must be `committed` or a known partial (`needs_recovery` with no `request_started` or `unknown` step). Unknown outcomes return `RESTORE_RECONCILE_FIRST`, so compensation never precedes reconciliation (INV-07). Restored targets return `RESTORE_ALREADY_RESTORED`; failed-before-write targets return `RESTORE_NOTHING_TO_RESTORE`.
- Conflict-aware content merge: a field changed by apply and edited later is a conflict. A field apply did not change keeps its later value without a conflict. Under a reverse note-type change, every later field edit is a conflict. Tags use a three-way merge: original tags, minus those the user removed after apply, plus those the user added after apply; tags apply added are removed. A card moved to another deck after apply is a deck conflict.
- Later study preserved: the expected restored state is built from the current note, so retained cards keep their IDs and current scheduling and history, including reviews after apply or conversion. Original scheduling is never restored.
- Separate restore intent, checkpoint and current snapshot: before any reverse effect, the restore requires a verified checkpoint covering the note, its cards and, for a reverse note-type change, both models. It stores an immutable restore intent (store schema 11 `restore_operations`, with the decision and the exact effects), publishes a fresh snapshot of the current state under the restore operation ID, and starts a new restore journal. The original apply snapshot and its receipt are never changed.
- Media before reference: original media referenced by the restored fields is checked. A file that is missing but archived in the apply snapshot is restored first with `store_media`. If the name now holds different bytes, the archived bytes are restored under a safe alternate name (`stem-lab<digest>.ext`), and `[sound:]`/`src` references in the restored fields are rewritten. Missing media that was not archived needs explicit acceptance. Apply's pre-write snapshot now archives the bytes of media its original fields reference, when the native port can read them (`ApplyPort::media_bytes`).
- Reverse effects: `restore_note` carries the precondition digest, an optional reverse mapping (current ordinal to original ordinal), the complete field set, the exact tag set, one deck per kept card and the explicit list of removed cards. A reverse note-type change needs the original note type to still exist with its ID; a retained card without a reverse mapping, a studied card that would be removed, a filtered-deck card, a deleted retained card, a deleted note or a later note-type change is a blocker. Unstudied new-task cards are removed only when listed.
- Created notes: the default keeps them. `delete_unstudied_created_note` is planned only when the note is listed in the decision, its content equals the applied state and no card has a review. Studied notes are kept and reported (`RESTORE_CREATED_NOTE_STUDIED`), and removal needs a separately authorized manual disaster-recovery procedure.
- Shared state: restore never deletes note types or collection media. Media that apply uploaded is listed as kept.
- Verification and receipt: every step is verified by read-back through the shared WP-11 step driver. The final read-back is compared with the expected post-state, stored as an asset with raw evidence, and saved as an immutable `RestoreReceipt` (`restore_receipts`) before the restore journal commits. Then the apply operation moves to `restored`. The store accepts `restored` only from `committed` or `needs_recovery`, only with unchanged step evidence and no unresolved step, and only when a committed restore journal with a receipt names that operation.
- Resume: a repeated `restore` for the same snapshot resumes the unresolved restore journal and never creates a second one. Steps are reconciled from native status and read-back: matching effects are adopted, pending rows are waited on, a request that never reached the ledger is resubmitted once with the same UUID, and unprovable absence stays in recovery. A receipt saved before a crash is reused, and a restore committed before the apply operation was finalized is finished. A refused restore (failed before write, or a known partial with only verified media) can be superseded by a new restore.
- Split (ALG-SPLIT): `linguist_application::split::apply_group` checks every unit (children, then the anchor) with the full apply preflight before any write. It snapshots the anchor source once under the execution ID and records the execution with one stable first-attempt operation ID per unit (`split_executions`, `split_attempts`), all before the first effect. Children are always created as fresh notes with their own markers, journals, snapshots and receipts. The anchor update or migration runs only after every child verifies. Any failure leaves an exact partial group (`verified`, `not_started`, `failed_before_write`, `needs_recovery`, `in_progress` per unit). Resume reconciles unresolved units with the same operation ID, starts a new attempt only for a unit proven to have no effect (or only verified media), and never recreates a verified child. A rolled-back group is never re-applied.
- Split review gate: `GRAMMAR_SPLIT_NATIVE_REVIEW` is now resolvable with `ReviewChoice::Anchor(anchor_id)`, which must name the anchor recorded in the unit's split request (`REVIEW_SPLIT_ANCHOR_MISMATCH` otherwise). A split unit applied alone returns `APPLY_SPLIT_GROUP_REQUIRED`.
- Group rollback (OP-44): `restore::plan_group_rollback` previews every apply operation that carries the group ID (an apply job group or a split execution), with existing-note restores (the split anchor) before created notes. `restore::rollback_group` runs one restore per reviewed decision; identity, session and local-durability faults stop the group, other failures are reported per item, and partial rollback is explicit.
- CLI: `snapshots restore SNAPSHOT [--decision FILE]` prints a local preview of what apply changed (fields, tags, deck moves, added cards, uploaded media, archived source media, existing restore operations) and exits 4 when blocked. `jobs rollback JOB [--item-id ID]...` prints the local preview for every apply operation of the group and the split execution status. `apply PLAN --split-group GROUP` previews the group's units with their roles and any execution status. Their `--apply` forms return `CAPABILITY_UNAVAILABLE` before any lease, checkpoint, journal or Anki request. `recover reconcile OPERATION` now names a restore journal's resume command. OP-44 and OP-50 are no longer unavailable routes.
- Native effects: `addons/linguist_bridge/effects.py` adds `restore_note` and `delete_unstudied_created_note`; `update_note` shares the mapped note-type helper. They are not registered, dispatched or packaged.

### Known limits — revisit after all packages

- No live mutation path. No Rust transport or `ApplyPort` adapter exists, and the companion neither registers nor dispatches `restore_note` or `delete_unstudied_created_note` (its ledger still accepts only `create_note`). `snapshots restore --apply`, `jobs rollback --apply` and `apply --split-group --apply` return `CAPABILITY_UNAVAILABLE`. Restore, rollback and split orchestration are verified only with the fake port (WP-03/WP-13/WP-15).
- Wire contracts are incomplete. The `restore_note` and `delete_unstudied_created_note` bodies are the application's serde shapes of `Effect`; there is no strict shared envelope, Rust parser or companion schema validation for them, and no approved staging path for `store_media` bytes (as in WP-11).
- Native atomicity is not established. `effects.restore_note` runs the note-type change, the field/tag update and one `set_deck` per card as separate backend calls outside a main-thread critical section; a crash between them leaves a partly restored note. Its card-set and precondition checks run before those calls, not inside one serialized operation, so a UI edit can still interleave. Undo boundaries are untested.
- CLI previews are local only. `snapshots restore` shows what apply changed from stored records; it does not read the collection, so it reports no live conflicts and no `observed_state_digest`. A `--decision` file is only checked for shape and snapshot; nothing in the CLI produces a live digest to bind it to. The live `plan_restore`, `restore`, `rollback_group` and `split::apply_group` are library-only. `jobs rollback` takes no per-item decisions.
- Restore journals cannot be rebound. Resuming a restore started in another collection session returns `RESTORE_SESSION_CHANGED`; there is no `ResumeBindingDecision` path for restore journals, so such a journal needs manual resolution. A new restore binds to the current session and requires the same stable identity as the apply operation (or its last rebinding decision).
- Restore issue codes reuse the WP-11 step-protocol codes (`APPLY_OUTCOME_UNKNOWN`, `APPLY_KNOWN_PARTIAL`, `APPLY_RESUBMIT_SAME_UUID`, and so on) inside restore journals; only their recovery command names `snapshots restore SNAPSHOT --apply`.
- Restore targets are limited. A restore of a restore, an imported legacy snapshot or a split-source snapshot is unsupported. For a known-partial target, conflicts are measured against the intended post-state, because no verified post-state exists. If the collection already equals the restore target, nothing is journaled, `RESTORE_NOTHING_TO_RESTORE` is reported and the apply operation stays `committed`.
- Merge support is per field. A field is restored, kept or replaced by reviewed text; there is no assisted text merge. A field the user changed back to its original value after apply still counts as a conflict. Under a reverse note-type change every later field edit is a conflict, and content in fields the original model lacks is discarded (it survives only in the restore's fresh snapshot).
- Tags are merged automatically without a decision. Anki's case-insensitive tag semantics are not modelled.
- Decks: retained cards return to the deck recorded in the apply snapshot; cards added by apply stay in their current deck. Deck existence is checked only by the companion effect, not in the preview.
- Card consequences are partly inferred. Cards added by an update (no note-type change) are always kept; Anki's Empty Cards tool is a manual step. Card generation when restored fields re-enable a template is not predicted; the read-back then mismatches and the restore needs recovery. A retained card deleted after apply, a deleted note or a later note-type change blocks restore with only a manual-recovery message; there is no disaster-recovery tooling, and original scheduling is never restored.
- The original note type must exist with its ID. Its manifest is not re-verified before a reverse note-type change; only the read-back compares the manifest digest, which still depends on the WP-11 stand-in digest gap.
- Media recovery depends on archived bytes. `ApplyPort::media_bytes` defaults to unavailable and no adapter implements it, so live apply snapshots would archive no source media; missing originals then need explicit acceptance. Alternate-name rewriting covers only exact `[sound:NAME]`, `src="NAME"` and `src='NAME'` forms, not percent-encoded or other syntaxes. Media uploaded by apply is never deleted; Check Media is a manual step.
- Created notes are kept unless listed. "Unchanged" compares fields, tags, model and card ordinals/decks with the applied state. If no note carries the marker, the restore reports nothing to restore. Studied created notes have no removal tooling.
- Checkpoints are not created by restore or split. The caller supplies a verified checkpoint ID; WP-10 limits apply (no live export, whole-collection packages, presence and lower-bound scope checks). A split group uses one checkpoint for all units, and cross-group reuse passes only by age and protected-manifest match.
- Split limits: the group preflight is checked again by each unit when it runs, so a change between preflight and the anchor's turn fails that unit, not the group start. Only an update anchor is tested; a migrating anchor, grammar media and Application tasks in split groups are untested. Each invocation starts at most one new attempt per unit. Any restored unit marks the whole group `rolled_back`, and it can only be applied again through a new plan revision. A partial group is never rolled back automatically. `plans resolve` decision templates do not offer the `Anchor` choice for `GRAMMAR_SPLIT_NATIVE_REVIEW`; the request must be written by hand.
- Group rollback scans every journal head to find a group (bounded to 10000 matches), orders anchors before created notes by action and then operation ID, classifies stop conditions by error-code prefix, and silently keeps any item without a decision (it is absent from the results). Apply jobs (WP-13) do not exist yet, so only split executions or callers that pass a `group_id` form groups.
- Local durability windows remain. The restore intent, the restore snapshot and the first restore journal version are separate SQLite transactions, as are the restore commit and the apply operation's move to `restored` (resume finishes the latter). Orphan restore intents are not listed by `recover inspect`. The restore receipt is built by the application from its own read-back, not received from the companion ledger.
- Store visibility: restore snapshots appear in `snapshots list` with post-state status `unknown`, and `snapshots list --status` has no `restored` filter. Decisions are stored only inside restore intents; decisions for refused attempts are not kept.
- Retention: schema 11 records (`restore_operations`, `restore_receipts`, `split_executions`, `split_attempts`) are immutable and not covered by any pruning rule yet (WP-14).
- Concurrency: the second-writer rejection is the store lease only; native owner fencing, expiry and concurrent UI edits during restore are untested.
- Evidence breadth: one Anki build (25.09.2), one disposable collection, vocabulary notes only (no grammar or split groups natively), no AnkiConnect, no real process-kill crash injection. Crash boundaries are simulated with fake-port faults and test-only journal tampering; "disk full" is a held SQLite write lock. INV-13 is shown at the effect level natively and end to end only on the fake port.
- Settings: restore and split consume no settings directly; `backup.reuse_max_age_seconds`, `media.max_asset_mb` and the package limit are passed by the caller.

## Package WP-13 — job executor

Source: [wp-13.md](wp-13.md)

Touch: `linguist-jobs`, core jobs and CLI handlers. Read ALG-JOB, ALG-RECONCILE and OP-35–47.

Steps: immutable modes/settings/selection, explicit run/resume authority, bounded prepare workers, serialized writer, controls/liveness, retry classification and independent item faults, grouped rollback plans, durable summaries/audit/tombstones. Remove state transitions that lose unknown outcomes.

Tests: pause/cancel during sent write, lease expiry while worker alive, no apply from prepare/simulate, resume without generation, per-item attempt budgets, halt on schema/identity fault, partial batch audit. Done when restart yields identical logical items and no duplicate collection creation.

### Completion audit — 2026-10-04

- Immutable modes, settings and selection (OP-35): `linguist_application::job_executor::create` freezes an approved, ready plan revision into a simulate or apply job (store schema 12 `apply_jobs`). The definition holds the exact plan digest, approval, ordered plan item IDs (plan order; all approved items or the `--item-id` subset), frozen effective settings, optional checkpoint (required for apply), protected-manifest digest and schema-change acceptance. Every item passes the WP-11 authorization (approval scope, digest, latest revision, readiness, standalone role) at creation; no Anki read occurs and nothing runs. Prepare jobs keep the WP-04/WP-05 selector path. A checkpoint created for a group (`group_id` in its evidence) makes that group the job ID, so every item reuses it as the same group; otherwise the WP-10 cross-group rule (age window and protected manifest) applies.
- Explicit run/resume authority (OP-39, OP-41): `job_executor::run` refuses `--apply` for simulate jobs (`JOB_MODE_NEVER_WRITES`) and requires the current `--apply` plus a caller-held collection-writer lease for apply jobs (`APPLY_FLAG_REQUIRED`, `APPLY_WRITER_LEASE_REQUIRED`), before any lease or event. The mode is fixed in the definition; nothing changes it on resume. Prepare jobs reject `jobs run --apply`, `jobs resume --apply` and `jobs retry --apply` in the CLI.
- Serialized writer and bounded work: one job lease (`JobWorker(job)`) per job, acquired with the WP-04 liveness rule (an expired lease of a live owner is never reclaimed), and one caller-supplied collection-writer lease. Apply items are dispatched one at a time in frozen order through `apply::apply_item_with`; the job adds no native effect of its own. Simulate items run `apply::simulate_item` (the full ALG-APPLY preflight, with the checkpoint gate only when the job names a checkpoint) and write no intent, snapshot or journal. Prepare jobs keep their bounded `jobs.prepare_workers` read waves.
- Durable item transitions (store `apply_job_events`): a hash-linked, append-only chain of `started` (attempt, stable operation ID and main-step ID allocated before any intent), `finished` (outcome, stable code, retry class), `control`, `retry` and `stopped` events. Worker events need the matching job lease inside the same SQLite transaction; a start also re-checks the newest control there, refuses a second unfinished start for an item (`APPLY_JOB_ITEM_IN_FLIGHT`) and enforces the attempt ceiling. A finish must follow its own start, or replace an unresolved (`needs_recovery`) outcome of the same attempt. `fold` derives per-item state (pending, started, committed, simulated, failed_before_write, failed, needs_recovery), attempts, operations and retry eligibility, and the job state (pending, running, interrupted, needs_recovery, halted, pause_requested, paused, cancel_requested, cancelled, completed, finished_with_failures).
- No lost unknown outcomes: on every run, before any control check or dispatch, each `started` or `needs_recovery` item is accounted for from durable evidence. A start with no intent record (or an intent with no journal) is proven to have had no effect and becomes `failed_before_write` (`JOB_ITEM_INTERRUPTED_BEFORE_INTENT`/`_BEFORE_JOURNAL`); it is dispatched again within the attempt budget. An intent with a journal is reconciled through WP-11 `apply::reconcile` with the same operation ID: a matching read-back is adopted, proven absence becomes `failed_before_write`, anything else stays `needs_recovery`. If any item stays unresolved the run stops with `RecoveryRequired` (exit 7) and dispatches nothing. Items are never reset to pending, and an unknown outcome is never retried.
- Controls and liveness (OP-40, OP-41, OP-43): pause/resume/cancel requests are `control` events; repeating the current request reuses its receipt; cancel is terminal (`APPLY_JOB_CANCEL_IS_TERMINAL`). A pause or cancel never interrupts a sent write: the current item finishes and records its durable outcome, the next start is refused inside its transaction, and the worker appends a `stopped` acknowledgement that names the control sequence. A request on an idle job (no active job lease, nothing in flight) is confirmed in the same transaction (`idle: true`). Otherwise `worker_stopped_confirmed` stays false until the worker acknowledges. Prepare jobs gain the same confirmation: the prepare worker acknowledges a pause/cancel after draining its wave (`preparation_stop_acks`), and an idle prepare job is confirmed by `jobs pause`/`jobs cancel`. `jobs show` reports the lease (none, released, active), expiry and owner liveness (alive, absent, unknown) without inferring death from expiry.
- Retry classification and independent item faults (OP-42): `job_executor::classify` maps stable codes to `transient` (dependency/transport, eligible), `halt` (shared identity, session, binding, revision/approval scope, model, checkpoint, capability, lease, store and local durability faults; eligible once the shared fault is fixed), `permanent` (item validation; needs a new revision, so a new job) and `reconcile` (unknown or partial native outcomes). A halt-class fault or an unknown outcome stops the group whatever `jobs.on_item_error` says; other failures continue past the item unless `jobs.on_item_error=stop`. A plain rerun never retries a failure: `request_retry` records an explicit envelope for eligible items only and refuses with `JOB_RETRY_RECONCILE_FIRST`, `JOB_RETRY_REQUIRES_NEW_REVISION`, `JOB_RETRY_ATTEMPTS_EXHAUSTED`, `JOB_RETRY_ALREADY_SUCCEEDED`, `JOB_RETRY_NOT_FAILED` or `JOB_RETRY_ALREADY_REQUESTED`. The per-item budget is the frozen `jobs.max_item_attempts`, counted from durable starts. Prepare retries are classified in the CLI without an envelope; `jobs run` retries their eligible failures as before.
- Grouped rollback plans (OP-44): every apply operation of a job carries the job ID as its journal group, so `restore::plan_group_rollback`/`rollback_group` (WP-12) and the `jobs rollback JOB` preview work on apply jobs. `job_executor::rollback_preview` lists one local restore preview per recorded operation of the selected items.

### Known limits — revisit after all packages

- No live execution. No `ApplyPort` adapter exists for reads or writes, so `jobs run` and `jobs resume` of simulate and apply jobs return `CAPABILITY_UNAVAILABLE`, and `jobs retry` of an apply job only records the envelope. The executor, reconciliation, controls during a write and halts are verified with the fake port only. All WP-11 and WP-12 native limits apply (no transport, incomplete wire contracts, no native atomicity, no AnkiConnect, one Anki build).
- Simulate mode is serial and live-read only. Simulate items run one at a time (no `jobs.prepare_workers` parallelism and no provider semaphores), need the same native read adapter, and give a time-bound preflight result that does not authorize apply. Without a checkpoint the gate is skipped and the job stores `protected_manifest_digest = "unchecked"`.
- Writer serialization depends on the caller. The job holds its own job lease; the collection-writer lease is supplied by the caller and keyed by a caller-chosen UUID. No canonical writer key is derived from the collection lineage, so two apply jobs with different writer keys could interleave. Duplicate application of one plan item is still refused by WP-11 `prior_attempts`.
- Heartbeats are per item. The apply executor renews the job lease before each item and accounting step, not during a long native call. `jobs.heartbeat_seconds` is validated (less than a third of the lease) and `jobs.pause_poll_ms` is validated, but the apply executor has no polling thread. A native call longer than `jobs.lease_seconds` lets the lease expire; the next event append then fails `LEASE_STALE_OR_EXPIRED`, leaving the item started for restart reconciliation.
- Controls act between items. A pause or cancel is honoured only between items, after reconciliation, and inside the start transaction; it never interrupts an item's media and main steps. Cancellation does not roll back committed items. A lease left active by a crashed worker blocks idle confirmation until a run reclaims the lease (owner proven absent) and reconciles.
- Liveness is Linux-only process identity (pid, start ticks, boot ID) on one host. The tests simulate a lost worker by appending events with a test lease and releasing it; no real process kill, no dead-pid reclaim, no multi-process race and no cross-host case is tested.
- Retry classification is a hand-written prefix table. Unknown codes default to `permanent`. Transient codes are the fake/read-adapter codes known today (`ANKI_READ_TIMEOUT`, `ANKI_DEPENDENCY_UNAVAILABLE`, `ANKI_HTTP_FAILURE`, `APPLY_OWNER_UNAVAILABLE`); real adapter codes may need reclassification. `halt` items are retry-eligible without checking that the shared fault was resolved (revision, approval or checkpoint faults fail again). Native refusals before write (`failed_before_write` with a code) use the same table.
- Permanent failures need a new job. Jobs are pinned to one revision; there is no add-input, revision rebinding or partial job re-creation. Interrupted-before-intent items are re-dispatched automatically on the next run and consume an attempt; once exhausted they stay `failed_before_write`.
- Restart reconciliation never rebinds. It calls `apply::reconcile` without a `ResumeBindingDecision`; a session change leaves the item `needs_recovery` and stops the job until `recover reconcile --rebind` (itself live-unavailable) resolves it. Operations later restored or compensated are reported as committed with code `APPLY_OPERATION_RESTORED`.
- One checkpoint per job. Items reuse the job's checkpoint; the job adopts the checkpoint's group as its ID only when the checkpoint was created for a group. Otherwise reuse needs `backup.reuse_max_age_seconds > 0` (default 0), and long jobs can outlive the window and halt with `CHECKPOINT_REUSE_REJECTED`. Nothing creates checkpoints per item or per job, and the CLI cannot compute the protected-manifest digest: `--protected-manifest` is caller-asserted.
- Split groups are excluded. Grammar split units are refused at creation (`APPLY_SPLIT_GROUP_REQUIRED`); they run only through `apply --split-group` (WP-12), not as job items.
- Rollback stays local in the CLI. `jobs rollback JOB` is the WP-12 local preview; live `rollback_group` is library-only and takes no CLI decisions. Rollback order and limits are those of WP-12.
- Audit and fold scale. Show, items, retry and audit fold the whole event chain on every call (bounded at 10,000 items and 200,000 events per job); there is no paged audit for apply jobs. The audit checks receipt presence and journal/item agreement, not snapshot contents, approval-evidence history or native state; `--live` is unavailable.
- Listing: `jobs list` has `--mode` and `--include-deleted` but no status filter (OP-36), and its entries changed to `kind`, `event_count` and `tombstoned` (prepare entries keep `checkpoint_count`).
- Tombstones are permanent and unpruned. There is no undelete, tombstones and schema 12 records are not covered by any retention rule (WP-14), and a tombstone does not block lease acquisition or `jobs recover` previews. Prepare jobs with exhausted failures can be tombstoned only after `jobs cancel`.
- Prepare-mode gaps that remain: prepare retries are classification only (no envelope; `jobs run` retries every eligible failure), prepare stop acknowledgements live in a separate table that references the control digest rather than the event chain, provider pacing, enrichment and partial batch plan publication are still pending, and `jobs recover` still covers only interrupted reads.
- `jobs migrate` (OP-47) still only upgrades local schema (now to 12, with the verified backup); importing legacy job files is not implemented. Older binaries cannot open a schema 12 store.
- Approval selection: without `--approval`, creation uses the only approval of the exact revision and digest and refuses ambiguity (`JOB_APPROVAL_AMBIGUOUS`); approvals carry no order.
- Settings: apply jobs consume `jobs.max_item_attempts`, `jobs.on_item_error`, `jobs.lease_seconds`, `backup.reuse_max_age_seconds`, `backup.max_package_gb` and `media.max_asset_mb` from the frozen settings; `jobs.prepare_workers` and `jobs.pause_poll_ms` affect prepare jobs only.
- Exit codes of `job_executor::run` (7 recovery required, 5 halted, 4 item failures) are library-level; the CLI never reaches them until execution is available.

### Known limits — revisit after all packages

Config import and activation:
- Only Python YAML (`config_version` 1, 2 or absent) and native JSON v1 are recognized; there is no v2+ version ladder, so `config migrate` without `--from-import` is still only the `already_current` no-op.
- Plain-scalar resolution is a hand-written approximation of PyYAML `safe_load`; it refuses (not interprets) dates, octal/hex/binary, sexagesimal and non-finite numbers. It is tested on the generated fixture and targeted cases, not differentially against PyYAML.
- The legacy default table is a one-time export of `legacy/src/.../config.py`; `anki.backup_dir`'s default is the placeholder `${HOME}/AnkiBackups`.
- Only English, Vietnamese and Japanese language labels are normalized; anything else is unresolved.
- Overrides are written where the value differs from the v2 builtin or any purpose preset, so a legacy global value (for example `learning.explanation_language = "en"`) overrides the `japanese_grammar` preset (`vi`). This is faithful to legacy behaviour and noted in the record detail, but it is not asked about.
- Records for keys absent from the file (`implicit_default`) are never blocking, even when the legacy default enabled a feature now unavailable (legacy defaulted browser fallback and vision adjudication to on).
- Custom prompts and schemas are exported but cannot be activated: custom prompt loading and non-builtin kanji schemas remain unavailable.
- Card task maps and target decks are never inferred; unsupported purposes stay report-only.
- Activation requires the exact candidate recorded in the report: to change it, activate and then use `config set`. Accepted keys appear only in the command receipt; they are not stored durably. The config lock is advisory (the prepublication byte check catches non-cooperating editors).
- Reports contain raw legacy values (deck names, paths, model names) other than URL credentials; they are private 0600 files but not otherwise redacted.

Resources:
- No remote catalogue and no builtin pinned manifests: the user supplies version, SHA-256 and license. The license must be in a hand-written SPDX allowlist and is recorded, not verified against the artifact.
- Builtin download hosts are a hand-picked GitHub/Hugging Face list; HTTPS downloads from them were not tested live (only the loopback fake server). No proxy support, no retries, no resume; the deadline is a fixed 60 × `network.request_timeout_seconds`.
- Only zip archives (stored/deflate; `zip` now enables `deflate-flate2-zlib-rs`) are supported; type checks are file-name based (`NAME.traineddata`).
- Free space is checked before the transfer and after staging, not while streaming.
- Tesseract packs share one `tessdata` directory: an upgrade needs manual removal, and `ocr.resource_path` is not set automatically. A crash between linking a pack and writing its receipt leaves an unreceipted pack, which `resources list` reports.
- There is no uninstall/remove command. Receipts are plain JSON files under `storage.resource_dir/receipts`, not store records.
- Ollama pulls use the loopback `llm.endpoint` only, without streaming progress; a digest mismatch leaves the pulled model in Ollama. Tested only against a fake local server.

Cache and ALG-GC:
- Reachability is a conservative heuristic: references are found as 64-hex runs in rows and in reachable assets. A reference stored only in compressed or base64 form would be missed (no such producer exists today). False positives keep assets.
- Any active lease blocks pruning, including a lease left by a crashed worker until `jobs recover` releases it; any pending journal blocks it too. The one-hour orphan grace is fixed.
- The census runs inside the immediate write transaction; concurrent writers wait up to `storage.sqlite_busy_timeout_ms` and may fail. Asset publication now holds the write lock while linking.
- Provider-cache deletions are not locked against readers (metadata-first deletion makes a concurrent read a miss), are not recorded in the store, and use fetch age, not per-purpose `cache.ttl_hours`. The budget spans provider entries and unreferenced store files only approximately.
- `cache prune --execute` opens the store with migration, so an older store is upgraded to schema 13 (with the usual verified backup). Older binaries cannot open schema 13.
- `gc_runs` and `gc_tombstones` grow without bound. Unmanaged files, `storage.temp_dir`, backups, receipts, journals, snapshots and WP-13 job tombstones are outside any retention rule; no history retention policy exists (by design).

Legacy job import:
- Only the legacy `batch_jobs`/`batch_items` SQLite schema, up to 100 MiB and 200,000 items. Artifacts and legacy snapshots are referenced by path/ID but not imported.
- Imported records are separate from v2 jobs: they are not shown by `jobs list`/`show`, cannot be converted into runnable jobs, and `requires_review` items have no resolution workflow beyond manual inspection.
- The WAL is copied but not the `-shm`; a legacy writer active during the copy can yield an inconsistent snapshot. Legacy settings JSON is retained verbatim.

Settings and diagnostics:
- Coverage is verified structurally (each consumer file names its setting) plus targeted behaviour tests; not every entry has a nondefault behaviour test.
- 11 settings are gated (browser executable/timeout/pages, audio endpoint/credential, custom dictionary template/schema, image custom endpoint, vision accept confidence and model, kanji prompt); unavailable selector values are listed in the coverage document. Dormant gated settings are only reported by `config validate`; ordinary commands do not refuse them. `browser.enabled = true` is reported by `config validate` and `doctor` but refused by no operation, since none uses the browser.
- `output.language` has one value (`en`). `output.color` colours only key paths of human output; `output.progress` prints a start line for config import, resource install and cache prune on an interactive stderr only — there are no progress bars.
- The diagnostic log records one line per invocation, only when `state.sqlite3` already exists, inside `state/logs` (so state is nonempty afterwards). Commands that fail before settings are resolved (and `config import`) are not logged. Rotation is not synchronized across concurrent processes; debug/trace only add the settings fingerprint.
- `storage.sqlite_busy_timeout_ms` is process-global and applied once settings resolve.
- `anki.commit_interval_seconds` paces apply-job items only (not single `apply` or split groups, and no live apply exists). `anki.native_adapter` is checked at job creation/run and at the CLI `apply`/`recover` entry, not in restore or backup paths.
- `filters.*` change only the dictionary lookup term (kanji and image queries are unchanged); `clean_word_only` also drops digits and punctuation, and the normalized term is visible only in the request URL.
- `purposes.<purpose>.ocr_languages` applies only when `--purpose` selects that purpose. `storage.backup_dir` is the default `backup create` output; the directory is not created. `selection.duplicate_policy = "skip_exact"` is refused at the CLI entry of `vocab`, `grammar` and `jobs create/run`.

#### Known limits — revisit after all packages

- **Compatibility.** Writes are verified only for companion 0.1.0 on Anki 25.09.2 (build `3d813c83`) with the pinned AnkiConnect 2055492159 bytes. Any other Anki or AnkiConnect build is read-only; the matrix is static in both the companion and the CLI.
- **Transport.** Writes require a loopback endpoint and an AnkiConnect API key; the key travels in plain HTTP on loopback. Remote writes are not supported.
- **Concurrency.** The companion accepts one in-flight operation at a time (`BRIDGE_OPERATION_PENDING`); there are no parallel writes. A new `labBegin` replaces the owner when nothing is in flight; protection against a second CLI relies on the local collection-writer lease, so two CLIs with different state directories fence each other (stale requests are refused) rather than queue.
- **Ledger resolution.** A companion row closed as `unknown` stays `unknown` in the companion ledger after the CLI adopts or rejects it from read-back; the CLI journal is the record of the resolution. Unknown rows do not block other operations.
- **Session identity.** Session change is exercised through companion restarts, a hook-driven close/reopen (the path full sync and import use), a profile switch and a lost sidecar. A real `.colpkg` import, an AnkiWeb full sync and same-file replacement by another process are not exercised. The epoch survives only the companion's own checkpoint export, by file identity and handle; a full sync during an export is not tested.
- **Fault injection.** ENOSPC is injected at the ledger `running` boundary (`LINGUIST_BRIDGE_FAULT_FILE`), not a full filesystem; ENOSPC inside a native effect or a collection write is not exercised. Crashes are process exits after the effect; power loss and fsync ordering are not tested. The fault hook ships in the add-on and is inert unless the environment variable names a file.
- **Checkpoints.** Native export writes whole-collection packages only (`backup create --scope affected` with `--apply` is refused). The collection is closed during export, so other AnkiConnect reads fail meanwhile. Very large collections can exceed `backup.verify_timeout_seconds` and end unknown. The CLI deletes the companion's export after its verified copy; staging files for media are not cleaned up.
- **Media.** Media-bearing apply and restore run through the effect probes (`verify-native-apply.py`, `verify-native-restore.py`) and fake-port tests, not through a desktop scenario.
- **Lenient numbers.** `findModelsByName` and note evidence are parsed with 64-bit integers and floats; only names, ordinals, templates, CSS, IDs within the safe range and integer/string evidence fields are used.
- **Evidence bounds.** `resolve-history` uses the bounded inspection (16 cards, 10 000 review rows, 1 MiB media, standard note types); larger notes fail closed. FSRS desired retention and decay are reported but not part of the compared scheduler projection (stability and difficulty are).
- **Review content.** `plans edit` can fill an empty `SenseKey` but cannot set grammar `UseKey`, prompts or examples; a grammar revamp from a sparse source needs `plans split-grammar` (authored units) to become ready.
- **Rollback.** `jobs rollback --apply` builds default decisions and refuses any group with conflicts or blockers; field and deck decisions need `snapshots restore --decision`. A restore journal whose session changed cannot be rebound (`RESTORE_SESSION_CHANGED`).
- **Apply jobs.** `jobs run`/`jobs resume` for simulate and apply jobs still return `CAPABILITY_UNAVAILABLE`; the job executor is not wired to `NativePort`.
- **Models.** `models install` creates the two fixed managed models only; managed model upgrades and other note types are not supported.
- **Evidence environment.** The desktop scenarios need Anki's Python, `/usr/bin/anki`, Linux and the AnkiConnect package (`LAB_ANKICONNECT_ZIP`); they are `#[ignore]` in `cargo test` and run by `scripts/release-check.py`. No CI runs them (RI-08).
