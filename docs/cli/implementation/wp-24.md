### Decisions

1. **Campaign.** A durable campaign record in the store holds the frozen selection, cohorts, batch size, decision policy and limits. Each batch has one phase: `selected → preparing → generating → reviewing → needs_agent → ready → approved → applying → verifying → done`, plus `paused`, `failed` and `deferred`. Each item records its phase, plan, jobs, who decided each issue (`policy` or `agent`) and its verification result. No campaign state lives in an agent's context.
2. **Tick.** `campaign run` advances every batch as far as it can without judgment, records each transition, and exits. It is idempotent: a second run or a kill at any point loses no work. A campaign lease prevents overlapping ticks. `--max-seconds` bounds one tick; long jobs resume on the next tick. A missing service (Anki, companion, Ollama, VOICEVOX, Tesseract) leaves the batch waiting, not failed.
3. **Pipelining.** Only one batch holds the collection-writer lease. While batch N applies, batch N+1 prepares and generates.
4. **Driver.** A systemd user timer (`Persistent=true`, every 15 min) runs `scripts/campaign-tick.sh`. The script runs `campaign run`, reads `campaign status --json`, and starts headless `claude -p "/campaign-tick"` only when a batch is `needs_agent`, `failed`, or stopped with `JOB_CHECKPOINT_SESSION_ENDED`. Quiet ticks cost no tokens. A daily cap bounds agent runs. Cloud routines cannot reach the local Anki, Ollama or VOICEVOX and are not used.
5. **Cohorts and order.** Batches never mix purposes. Order: classifier calibration (no writes) → pilot (20 plain Japanese notes) → Japanese plain → Japanese kana-only → Japanese without recording or picture → English → Japanese/English split candidates → duplicate merges (14 groups) → OCR vocabulary (10) → grammar (538, with its own 5-note pilot). A cohort starts only after the previous one has no `paused` batch.
6. **Batch size.** Default 100 notes, one apply job and one checkpoint each (≈190 batches). Grammar batches are 10 notes, because OCR review and splits make them large.
7. **Decision policy.** The policy file is read by `plans resolve-batch --policy`. It holds the user's standing preferences from WP-20 to WP-23:
   - native history map 0/1/2 = comprehension/production/spelling; a note's missing ordinal is skipped;
   - Spelling on unless the source says blank (`y`, `ｙ` and `<font>y</font>` count as yes); kana words get an audio-only Spelling front;
   - sense: the dictionary sense whose reading equals the source reading, then the first common one; more than one candidate with equal rank goes to the agent;
   - pictures (user decision 2026-10-11: remove every dictionary screenshot, keep visual-recall images): every vocabulary job runs with `images.existing_policy=inspect`, so each source image is OCR'd and sorted by `ocr_inspection::classify` (`ocr-layout-heuristic-v1`). `Illustration` is kept as the Picture; `Dictionary` (and grammar pages) is archived, not rendered; stroke GIFs are archived. `Mixed` and `Uncertain` (`IMAGE_CLASSIFICATION_REVIEW`) go to the agent, who looks at the image. The file name (pasted or screenshot) is never the deciding signal: a screenshot can be a picture and a paste can be a dictionary page. With no kept picture, pick the first いらすとや candidate, then Commons; none found goes to the agent;
   - audio: keep the note's own recording; without one, VOICEVOX for Japanese and the dictionary recording for English;
   - Extra Info (Hán-Việt) is archived, not rendered;
   - generated facts: accept those that pass the mechanical checks (Godan, katakana, schema); others go to the agent.
   Any issue the policy cannot decide moves only that item to `needs_agent`.
8. **Agent role.** The skill `.claude/skills/campaign-tick` tells the agent to:
   - read `campaign status --json`;
   - decide `needs_agent` items from their templates (it can view screenshots and candidate pictures);
   - check OCR against the screenshot for grammar;
   - spot-check 10 % of policy-generated facts per batch; if more than 2 are wrong, the batch is regenerated with `llm.provider=claude_code`;
   - approve `ready` batches, update the review sheet, and exit.
   Each decision and approval is recorded with `actor=claude-agent`. A fresh session needs nothing from an earlier one.
9. **Agent approves and applies** (user decision). Every apply still takes a verified checkpoint and can be rolled back per job.
10. **Guardrails.**
    - Headless permissions allow only `campaign`, `plans show|resolve-batch|bind|validate|approve|split-vocab|split-grammar|merge-notes` and `jobs show|items`. They deny `rollback`, `restore`, `models install`, `notes delete` and anything outside the CLI.
    - The campaign deletes a note only as the second step of a duplicate merge (Decision 17), after the survivor is applied and verified and inside that batch's checkpoint. It deletes nothing else.
    - The campaign pauses itself on any of these: an identity, schema or session fault other than a plain session end; a failed post-apply check (card ID, ordinal, review count lower than before, review log lost, missing media); an unknown outcome reconcile cannot settle; more than 20 % agent-decided items in a batch; a spot-check failure after regeneration. The agent cannot resume a paused campaign; the user runs `campaign resume`.
    - Reviews the user does while a batch runs are expected: verification allows a higher review count only when the new review-log entries are newer than the checkpoint.
11. **Generation is a checkpointed job stage**, after enrichment, with one event per item.
12. **Session end.** After `JOB_CHECKPOINT_SESSION_ENDED` the campaign reconciles the stopped items, then creates the follow-up job and its checkpoint itself.
13. **Split groups** in a batch are applied after its other items, one checkpoint per group through `split::apply_group`, and units inherit the schedule (WP-23).
14. **Checkpoint retention.** The campaign keeps the checkpoints of unfinished batches and of the last 5 `done` batches, and deletes older checkpoints that it created. It never touches checkpoints it did not create (the 93 existing ones).
15. **Revision compaction.** `resolve-batch` publishes one revision per pass, not per decision.
16. **Full sync** (user decision 2026-10-11). The campaign keeps going without syncs; the user closes it manually and then syncs to AnkiWeb once, choosing **Upload**. Until then:
    - reviews must be done only in this desktop profile: reviews on a phone or AnkiWeb after the last sync are lost by the final Upload;
    - Anki's automatic sync on profile open/close should be off, so a full-sync prompt never blocks the desktop (and AnkiConnect) or offers Download;
    - the agent never syncs; `campaign status` repeats the reminder and the count of applied notes waiting for the Upload.
17. **Duplicates are merged** (user decision 2026-10-11). Groups: the 7 Japanese and 5 English same word+reading groups, 私 (Picture Words and v3), and the stale v2 歩留まり into its v3 note 1791454072963. In each group the survivor is the note with the most reviews (ties: the oldest). Its plan takes the union of the group's senses, pictures, recordings and archived sources; the merged notes' content is archived on the survivor. Order inside the batch: apply and verify the survivor, then delete the other notes through the companion. The deleted notes' cards and their schedules are gone from the collection (their review log rows stay in Anki's revlog, orphaned); this is the cost the user accepted. Merge groups run in their own cohort after the plain cohorts, with one checkpoint per group, and the agent confirms each group (homographs such as 本 may be two senses that the survivor keeps side by side).

### Implementation

**M1 — store (schema 14 → 15).**
- `crates/linguist-store/src/campaign.rs`: tables `campaigns` (immutable definition: selection, cohorts, batch size, policy digest, limits, settings digest), `campaign_batches`, `campaign_items`, `campaign_events` (append-only, CAS on head like job events), and `campaign_checkpoints` (ID, batch, created_by_campaign, pruned_at).
- `campaign_leases` reuses `lease.rs`.
- Migration in `lib.rs` (`SCHEMA = 15`), with a forward test and refusal of older binaries.
- Contracts: `contracts/v2/campaign.schema.json`, `campaign-status.schema.json` and `review-policy.schema.json`, plus fixtures.

**M2 — generation as a job stage.**
- `jobs::prepare_document` gains a generation step after enrichment when the job freezes `generate=true`. A `generated` checkpoint event in `preparation.rs` holds the certified draft, so a crash never generates an item twice.
- Failures: `GENERATION_TRANSIENT` (retryable; engine down or timeout) and `GENERATION_REVIEW_REQUIRED`.
- The provider chain (Local → Claude Code → Codex) is frozen per job.
- `plans generate --all-items` stays for single plans.

**M3 — decision policy.**
- `crates/linguist-application/src/review/policy.rs` holds the rules of Decision 7. It is pure: it takes an issue and its templates and returns a choice or `undecided` with a reason.
- `resolve-batch --policy FILE` runs the policy before the batch's own decisions and writes `undecided` items to the output.
- `review/batch.rs` publishes one revision per pass.
- Port the remaining rules of `target/lab/wp20/batch.py` and `target/lab/wp19/review_v3.py`; the lab drivers are then retired.

**M4 — campaign engine** (`crates/linguist-application/src/campaign.rs`). The tick state machine:
- `selected → preparing`: create a prepare job (`generate=true`) for the batch's note IDs.
- `preparing/generating`: `jobs run` until every item is captured and generated or failed; retry transient failures within `jobs.max_item_attempts`.
- `reviewing`: `resolve-batch --policy`; split candidates get `plans split-vocab|split-grammar` from the policy or the agent.
- `ready → approved`: `plans bind`, `validate`, then `approve`. Approval is the agent's step; with `campaign approve` it can also be the user's.
- `applying`: `jobs create --mode apply --create-checkpoint`, then `jobs run --apply`; split groups follow; session end leads to reconcile and a follow-up job.
- `verifying`: compare each note's cards with the pre-apply snapshot (Decision 10) and check media references. This ports `target/lab/wp20/verify.py` and `wp23/verify.py`.
- `merging` (duplicate cohort only): after the survivor verifies, `delete_note` for each merged note, then read back that it is gone and the survivor is unchanged.
- `done`: run checkpoint retention; update the review-sheet data.

**M4b — duplicate merge.**
- Selection-time grouping by normalized word and reading (vocabulary), recorded as merge groups in the campaign definition; a new duplicate created later is not merged by this campaign.
- `plans merge-notes PLAN --survivor N --merge N...`: one document that unions the group's sources; review issues as for a split.
- Companion 0.5.0: `delete_note` native effect with a precondition (note ID, model, field digest, card IDs) and a journal step; refused for a note with an unknown outcome. `VERIFIED_COMPANIONS` updated.
- Rollback of a merge group re-imports the deleted notes from the group's checkpoint with their original note and card IDs, schedules and review log (`restore` of a deleted note; new restore path, tested on a disposable profile before any real merge).

**M5 — CLI** (`crates/linguist-cli/src/campaign.rs`, kept out of the 5,268-line `main.rs`).
- `campaign create --cohort ... --batch-size N --policy FILE`
- `campaign run [--max-seconds S]`
- `campaign status [--json]`, with `next_actions` and per-item templates
- `campaign items CAMPAIGN [--phase P]`
- `campaign approve BATCH`
- `campaign pause|resume|cancel`
- `campaign defer ITEM`
- `campaign install-timer`
- Docs: `docs/cli/operations/campaign.md` (OP-62–OP-69) and a new campaign algorithm section in `docs/cli/recovery/jobs.md`. Raise the operation (1–69), algorithm (19) and package (1–24) counts in `docs/cli/validate.py`.

**M6 — guardrails.** Pause conditions (Decision 10), each with a typed code (`CAMPAIGN_PAUSED_VERIFY`, `CAMPAIGN_PAUSED_IDENTITY`, `CAMPAIGN_PAUSED_AGENT_SHARE`, `CAMPAIGN_PAUSED_SPOT_CHECK`, `CAMPAIGN_PAUSED_UNKNOWN_OUTCOME`). `campaign resume` is refused unless a TTY is attached or `--by-user` is given; the headless allowlist omits it.

**M7 — agent driver.**

| picture | 0 | 2 (0.412, 0.463) | 16 |

### Known limits — revisit after all packages

- **Generated content quality.** The local `gemma4:12b` still writes weak facts (a collocation that repeats the word, awkward examples such as 軍の制裁を受ける). The policy accepts generated facts and rejects only a collocation or contrast that names the word itself; the agent spot-checks 10 % of each batch. The fallback chain (`claude_code`, `codex`) runs only when the local model fails and uses the user's quota.
- **Picture candidates.** With no kept picture the policy takes the first candidate (いらすとや first, then Commons). Commons searches by gloss sometimes return a text-heavy image (形容詞 got a Walloon adjective table). The picture candidate is not classified by OCR.
- **Classifier calibration** used 91 images (63 notes). Pictures that carry much text (a labelled diagram) can still score in the uncertain band and go to the agent; a dictionary page that scores 0.43 or lower would be kept as a picture.
- **Store growth.** Plan revisions store complete plan bodies. Chained generation (one revision per 10 drafts), one revision per policy pass and digest-referenced provider pages keep a 100-note batch to tens of revisions of a few MB, but the store (32 GB before the campaign) keeps growing; nothing compacts revision history.
- **Checkpoint per batch.** Each apply job exports and verifies its own full-collection checkpoint (3.6 GB, 2–12 min). Retention deletes those of `done` batches beyond the newest 5; a checkpoint left by a job orphaned by a kill is recorded and pruned, the orphan job itself stays in `jobs list` unrun.
- **Merge.** A merged note's own card history is deleted with it (its review rows stay in Anki's revlog); `notes restore-merged` brings it back with IDs, schedule and review rows, but not FSRS memory state or custom data beyond `cd`. Merges need companion 0.5.0 (installed 2026-10-12). The two cross-type groups (私 v3 + Picture Words; 歩留まり v3 + stale v2) use explicit survivors.
- **Survivor archive only.** Duplicates' fields and media are archived on the survivor's plan item, not rendered on the survivor card.
- **Spelling cards.** The uniform history map keeps every existing card; a note whose source said "no spelling" (blank Test Spelling, 51 notes) can still receive a Spelling card from the target model's template rule.
- **OCR vocabulary and grammar** depend on the agent comparing OCR text with screenshots (`OCR_TEXT_REVIEW` for `ja_ocr`, `GRAMMAR_OCR_NEEDS_AGENT`); agent cost grows with the 538 grammar notes.
- **Agent approvals.** The agent's approval is bounded by the agent-share limit (20 %) and the pilot review; it is not a human review of every card.
- **Sync.** Nothing syncs until the user closes the campaign and chooses **Upload**; reviews on other devices meanwhile are lost by that Upload.
- **Tick wrapper.** `scripts/campaign-tick.sh` starts Anki and VOICEVOX when asked (`LAB_START_ANKI`, `LAB_START_VOICEVOX`); Anki's own full-sync prompt on start or close would block it.
- **Lane parallelism.** One write step and one prepare step run at a time; generation (local model) is the slowest stage, so throughput is about one batch per generation run.
