## WP-21 — batch processing (prepare → review → apply jobs)

Status: complete 2026-10-10. Core done 2026-10-09; `plans resolve-batch` and full-pipeline prepare jobs added 2026-10-10 (see both completion audits).

### Goal

Many notes (a query, a deck, or a list of note IDs) go through the full pipeline the single-note path already supports:

- dictionary;
- kanji;
- pictures;
- audio;
- certified LLM generation;
- review;
- one approval;
- one checkpoint;
- an apply job that can be paused, resumed, retried and rolled back.

The batch must give the same results as running each note alone.

### Where things stand

- `vocab revamp --query Q --limit N` and `--note-id` (repeatable) already prepare one plan with N documents. Check that dictionary, enrichment and generation run for every document, not just the first.
- `jobs create --mode prepare` refuses any dictionary other than `authored`: `crates/linguist-application/src/jobs.rs:189` returns "durable jobs currently capture source drafts only; dictionary enrichment checkpoints are pending".
- `jobs create/run/resume --mode simulate|apply` returns `CAPABILITY_UNAVAILABLE` at `crates/linguist-cli/src/main.rs:4108` (RI-09). The executor in `crates/linguist-application/src/job_executor.rs` and its fake-port tests in `crates/linguist-application/tests/jobs_apply.rs` (pause/resume, no duplicates) exist. The CLI is not wired to `NativePort` (`crates/linguist-application/src/native_port.rs`, `crates/linguist-cli/src/native_writes.rs`).
- `apply --apply` on a multi-item plan applies item by item. Each call takes its own full-collection checkpoint, about 3.6 GB and 2–3 minutes on the user's collection. 50 items would mean about 180 GB and 2.5 hours, which is the main reason for apply jobs.
- `~/.local/state/linguist-anki-bridge/backups` already holds 72 GB (21 checkpoints). Plan the retention: `backup list`, the reuse rule (`backup.reuse_max_age_seconds`) and the existing gc commands.
- Reviews are bound to the document digest, so a content-changing decision (sense, media role) reopens the others. Generation clears all decisions. Single-note runs loop until stable. See the WP-19 known limits.
- `plans regenerate --stage generation` fails once a sense is chosen (WP-19 known limit); use `plans generate` on a fresh plan.

After a restart or a full sync, a resumed job reconciles unfinished items, then stops before dispatch with `JOB_CHECKPOINT_SESSION_ENDED`. Its `next_commands` names a follow-up `jobs create ... --item-id ... --create-checkpoint` for the pending items.

### Completion audit 2026-10-10

**Batch review (step 4).** Commits `7714b78` and this milestone.
- `plans resolve-batch PLAN --decisions FILE` applies a JSON list of decisions bound to the latest revision and, each, to its document's digest at that revision; `--template --actor NAME` prints the file for every open review issue with every `choice` null. Schema `contracts/v2/resolution-batch.schema.json`; docs in [plans](../operations/plans.md).
- Order: source media roles first, then sense (and other identity decisions), cue repairs, native history, source verifications, candidate media, generated facts, and `expect_resolved` assertions last. This differs from the step-4 order (sense, media roles, history, ...): on the user's data a source media role that changes the document clears every earlier decision on it (core rule), so a sense decided first was lost.
- Even in the best order a later content change can invalidate an earlier decision (two media roles on one note clear each other). After the ordered pass, any decision whose issue reopened is re-applied unchanged and revalidated, at most four passes (`REVIEW_BATCH_NOT_STABLE`). The lab driver did the same by looping until no issue was open.
- `SOURCE_TASK_MAPPING_REVIEW` has no decision; the native history task map closes it. The template marks it `expect_resolved`, an assertion checked after all decisions.
- Proof on the user's collection (local state only, no Anki writes): 3 unflagged `2. Picture Words` notes (大人 1585320449222, 午後 1585320889021, 空気 1585321315359) prepared by a job; 32 decisions and 3 assertions resolved in 2 passes and 2.4 s; the plan was ready. The first run, with the step-4 order and one pass, ended with 9 issues reopened; that run is why the order and the passes changed.

### Known limits — revisit after all packages

- **Batch review: one revision per decision.** `plans resolve-batch` publishes every decision (and every re-application) as its own revision, as N `plans resolve` calls would: 32 revisions for 3 notes. Plan history grows quickly; nothing compacts it.
- **Batch review: re-application.** A decision that a later content change reopens is re-applied with the same choice. The choice was made against the earlier content; resolve revalidates the evidence, but a reviewer is not shown the changed content again. Four passes bound the loop; no real plan has needed more than two.
- **Batch review: no generated-fact proof on real data.** The live batch had no generated facts (generation needs a chosen sense). `content_verified`/`content_rejected` ordering is unit-tested only. Split groups (`plans split-vocab`/`split-grammar`) are not part of the template; they still run before the batch.
- **Batch review: history map is uniform per file.** Each `history_map` entry is written by the reviewer; the template leaves it empty. Notes with different source models need different maps.
- **Prepare jobs: one revision.** A job publishes one revision with every stage's result; `vocab revamp` publishes one per stage (source, dictionary, enrichment). `plans regenerate --stage` works on either, but `plans diff` cannot show the stages of a job plan separately.
- **Prepare jobs: failure detail.** A failed item records only its code (`ENRICHMENT_FAILED`, `ENRICHMENT_PROVIDER_TRANSIENT`); the provider's error text is not checkpointed. Run `vocab revamp --note-id N` on that note to see it.
- **Prepare jobs: generation.** LLM generation is not part of a prepare job; run `plans generate --all-items` after the job, which is not checkpointed per item (a crash re-generates every item).
- **Prepare jobs: fake-only end-to-end failure paths.** Transient-provider retry and `ENRICHMENT_FAILED` are covered by the classification unit test and the store; no test injects a provider failure into a running job.
- **Session-bound checkpoints.** A crash or restart mid-job always needs a follow-up job and a second checkpoint, and rollback is then per job (two groups). Re-binding a checkpoint to a new session of the same collection is deliberately not allowed (RI-11).
- **Fault injection.** The companion fires a fault on the first matching point and variant only. The scenario places the crash with a variant (`store_media`), not by item count.
- **Split groups and jobs.** Vocabulary and grammar split groups are applied with `apply --split-group`, one checkpoint per group; apply jobs refuse split units.
- **Writer lease length.** The writer lease is renewed with `jobs.lease_seconds` (default 60). One item longer than that (very large media) can lose the lease mid-item; this was not tested.
- **Retention.** Checkpoints accumulate (177 GB in 52 files after WP-20); no retention policy runs automatically.
- **Release check.** See the WP-20 audit for the full run.
