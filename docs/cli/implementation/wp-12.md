# Implementation work package

Read [package dependencies and architecture](README.md) and the task-referenced OP/ALG records before coding.

## WP-12 — restore/splits

Touch: existing application restore orchestration, snapshots/group journals. Read ALG-SPLIT, ALG-RESTORE and OP-44, OP-50.

Steps: child stable IDs/anchor ordering, known partial recovery, separate restore intent/checkpoint/current snapshot, media-before-reference order, conflict-aware content merge, retained later study preservation, explicit created-note/task loss review. Avoid deletion of shared schema/source media.

Tests: child accepted/anchor failed, repeated resume no duplicates, every reverse effect crash boundary, later personal edit/review, studied child protection, reverse mapping incompatibility, unchanged original receipt and source archive. Done when grouped operation can safely resume or report exact unsupported recovery instead of claiming rollback success.

## Completion audit — 2026-10-04

- Restore (ALG-RESTORE, OP-50): `linguist_application::restore::plan_restore` is the live preview. It loads the snapshot, the frozen apply intent and its journal, checks collection identity and loopback, and reads the current note, media and models. It reports a field, tag, model, per-card deck, card and media diff with the history consequences, the conflicts that need a decision, and the blockers that make recovery unsupported. `restore::restore` needs the current invocation's `--apply`, the store lease, and a `RestoreDecision` whose `observed_state_digest` equals the preview. There is no force flag: each conflict needs its own field choice (`original`, `current` or reviewed `merged` text), deck choice, card-removal entry, missing-media acceptance or schema-change acceptance.
- Targets: only snapshots of apply operations can be restored. Imported, split-source and restore snapshots return `RESTORE_TARGET_UNSUPPORTED` (inspect/export only). The target must be `committed` or a known partial (`needs_recovery` with no `request_started` or `unknown` step). Unknown outcomes return `RESTORE_RECONCILE_FIRST`, so compensation never precedes reconciliation (INV-07). Restored targets return `RESTORE_ALREADY_RESTORED`; failed-before-write targets return `RESTORE_NOTHING_TO_RESTORE`.
- Conflict-aware content merge: a field changed by apply and edited later is a conflict. A field apply did not change keeps its later value without a conflict. Under a reverse note-type change, every later field edit is a conflict. Tags use a three-way merge: original tags, minus those the user removed after apply, plus those the user added after apply; tags apply added are removed. A card moved to another deck after apply is a deck conflict.
- Later study preserved: the expected restored state is built from the current note, so retained cards keep their IDs and current scheduling and history, including reviews after apply or conversion. Original scheduling is never restored.
- Separate restore intent, checkpoint and current snapshot: before any reverse effect, the restore requires a verified checkpoint covering the note, its cards and, for a reverse note-type change, both models. It stores an immutable restore intent (store schema 11 `restore_operations`, with the decision and the exact effects), publishes a fresh snapshot of the current state under the restore operation ID, and starts a new restore journal. The original apply snapshot and its receipt are never changed.
- Media before reference: original media referenced by the restored fields is checked. A file that is missing but archived in the apply snapshot is restored first with `store_media`. If the name now holds different bytes, the archived bytes are restored under a safe alternate name (`stem-lab<digest>.ext`), and `[sound:]`/`src` references in the restored fields are rewritten. Missing media that was not archived needs explicit acceptance. Apply's pre-write snapshot now archives the bytes of media its original fields reference, when the native port can read them (`ApplyPort::media_bytes`).
- Reverse effects: `restore_note` carries the precondition digest, an optional reverse mapping (current ordinal to original ordinal), the complete field set, the exact tag set, one deck per kept card and the explicit list of removed cards. A reverse note-type change needs the original note type to still exist with its ID; a retained card without a reverse mapping, a studied card that would be removed, a filtered-deck card, a deleted retained card, a deleted note or a later note-type change is a blocker. Unstudied new-task cards are removed only when listed.
- Created notes: the default keeps them. `delete_unstudied_created_note` is planned only when the note is listed in the decision, its content equals the applied state and no card has a review. Studied notes are kept and reported (`RESTORE_CREATED_NOTE_STUDIED`), and removal needs a separately authorized manual disaster-recovery procedure.
- Shared state: restore never deletes note types or collection media. Media that apply uploaded is listed as kept.
- Verification and receipt: every step is verified by read-back through the shared WP-11 step driver. The final read-back is compared with the expected post-state, stored as an asset with raw evidence, and saved as an immutable `RestoreReceipt` (`restore_receipts`) before the restore journal commits. Then the apply operation moves to `restored`. The store accepts `restored` only from `committed` or `needs_recovery`, only with unchanged step evidence and no unresolved step, and only when a committed restore journal with a receipt names that operation.
- Resume: a repeated `restore` for the same snapshot resumes the unresolved restore journal and never creates a second one. Steps are reconciled from native status and read-back: matching effects are adopted, pending rows are waited on, a request that never reached the ledger is resubmitted once with the same UUID, and unprovable absence stays in recovery. A receipt saved before a crash is reused, and a restore committed before the apply operation was finalized is finished. A refused restore (failed before write, or a known partial with only verified media) can be superseded by a new restore.
- Split (ALG-SPLIT): `linguist_application::split::apply_group` checks every unit (children, then the anchor) with the full apply preflight before any write. It snapshots the anchor source once under the execution ID and records the execution with one stable first-attempt operation ID per unit (`split_executions`, `split_attempts`), all before the first effect. Children are always created as fresh notes with their own markers, journals, snapshots and receipts. The anchor update or migration runs only after every child verifies. Any failure leaves an exact partial group (`verified`, `not_started`, `failed_before_write`, `needs_recovery`, `in_progress` per unit). Resume reconciles unresolved units with the same operation ID, starts a new attempt only for a unit proven to have no effect (or only verified media), and never recreates a verified child. A rolled-back group is never re-applied.
- Split review gate: `GRAMMAR_SPLIT_NATIVE_REVIEW` is now resolvable with `ReviewChoice::Anchor(anchor_id)`, which must name the anchor recorded in the unit's split request (`REVIEW_SPLIT_ANCHOR_MISMATCH` otherwise). A split unit applied alone returns `APPLY_SPLIT_GROUP_REQUIRED`.
- Group rollback (OP-44): `restore::plan_group_rollback` previews every apply operation that carries the group ID (an apply job group or a split execution), with existing-note restores (the split anchor) before created notes. `restore::rollback_group` runs one restore per reviewed decision; identity, session and local-durability faults stop the group, other failures are reported per item, and partial rollback is explicit.
- CLI: `snapshots restore SNAPSHOT [--decision FILE]` prints a local preview of what apply changed (fields, tags, deck moves, added cards, uploaded media, archived source media, existing restore operations) and exits 4 when blocked. `jobs rollback JOB [--item-id ID]...` prints the local preview for every apply operation of the group and the split execution status. `apply PLAN --split-group GROUP` previews the group's units with their roles and any execution status. Their `--apply` forms return `CAPABILITY_UNAVAILABLE` before any lease, checkpoint, journal or Anki request. `recover reconcile OPERATION` now names a restore journal's resume command. OP-44 and OP-50 are no longer unavailable routes.
- Native effects: `addons/linguist_bridge/effects.py` adds `restore_note` and `delete_unstudied_created_note`; `update_note` shares the mapped note-type helper. They are not registered, dispatched or packaged.

Tests: `crates/linguist-application/tests/restore.rs` (19 fake-port tests) covers restore after later study with content, tags and decks restored and the later review kept; later personal edits, a later tag and a moved card as conflicts that refuse with zero effects until an explicit merged field and deck choice; Done criterion: a grammar split group resumes from any recorded partial state without recreating verified children, and a restore either finishes from its own journal with a verified receipt or reports the exact unsupported recovery (`RESTORE_UNSUPPORTED`, `RESTORE_RECONCILE_FIRST`, `RESTORE_SESSION_CHANGED`, `needs_recovery` with the resume command) instead of claiming rollback success. ## Known limits — revisit after all packages

- No live mutation path. No Rust transport or `ApplyPort` adapter exists, and the companion neither registers nor dispatches `restore_note` or `delete_unstudied_created_note` (its ledger still accepts only `create_note`). `snapshots restore --apply`, `jobs rollback --apply` and `apply --split-group --apply` return `CAPABILITY_UNAVAILABLE`. Restore, rollback and split orchestration are verified only with the fake port (WP-03/WP-13/WP-15).
- Wire contracts are incomplete. The `restore_note` and `delete_unstudied_created_note` bodies are the application's serde shapes of `Effect`; there is no strict shared envelope, Rust parser or companion schema validation for them, and no approved staging path for `store_media` bytes (as in WP-11).
- Native atomicity is not established. `effects.restore_note` runs the note-type change, the field/tag update and one `set_deck` per card as separate backend calls outside a main-thread critical section; a crash between them leaves a partly restored note. Its card-set and precondition checks run before those calls, not inside one serialized operation, so a UI edit can still interleave. Undo boundaries are untested.
- CLI previews are local only. `snapshots restore` shows what apply changed from stored records; it does not read the collection, so it reports no live conflicts and no `observed_state_digest`. A `--decision` file is only checked for shape and snapshot; nothing in the CLI produces a live digest to bind it to. The live `plan_restore`, `restore`, `rollback_group` and `split::apply_group` are library-only. `jobs rollback` takes no per-item decisions.
- Restore journals cannot be rebound. Resuming a restore started in another collection session returns `RESTORE_SESSION_CHANGED`; there is no `ResumeBindingDecision` path for restore journals, so such a journal needs manual resolution. A new restore binds to the current session and requires the same stable identity as the apply operation (or its last rebinding decision).
- Restore issue codes reuse the WP-11 step-protocol codes (`APPLY_OUTCOME_UNKNOWN`, `APPLY_KNOWN_PARTIAL`, `APPLY_RESUBMIT_SAME_UUID`, and so on) inside restore journals; only their recovery command names `snapshots restore SNAPSHOT --apply`.
- Restore targets are limited. A restore of a restore, an imported legacy snapshot or a split-source snapshot is unsupported. For a known-partial target, conflicts are measured against the intended post-state, because no verified post-state exists. If the collection already equals the restore target, nothing is journaled, `RESTORE_NOTHING_TO_RESTORE` is reported and the apply operation stays `committed`.
- Merge support is per field. A field is restored, kept or replaced by reviewed text; there is no assisted text merge. A field the user changed back to its original value after apply still counts as a conflict. Under a reverse note-type change every later field edit is a conflict, and content in fields the original model lacks is discarded (it survives only in the restore's fresh snapshot).
- Tags are merged automatically without a decision. Anki's case-insensitive tag semantics are not modelled.
- Decks: retained cards return to the deck recorded in the apply snapshot; cards added by apply stay in their current deck. Deck existence is checked only by the companion effect, not in the preview.
- Card consequences are partly inferred. Cards added by an update (no note-type change) are always kept; Anki's Empty Cards tool is a manual step. Card generation when restored fields re-enable a template is not predicted; the read-back then mismatches and the restore needs recovery. A retained card deleted after apply, a deleted note or a later note-type change blocks restore with only a manual-recovery message; there is no disaster-recovery tooling, and original scheduling is never restored.
- The original note type must exist with its ID. Its manifest is not re-verified before a reverse note-type change; only the read-back compares the manifest digest, which still depends on the WP-11 stand-in digest gap.
- Media recovery depends on archived bytes. `ApplyPort::media_bytes` defaults to unavailable and no adapter implements it, so live apply snapshots would archive no source media; missing originals then need explicit acceptance. Alternate-name rewriting covers only exact `[sound:NAME]`, `src="NAME"` and `src='NAME'` forms, not percent-encoded or other syntaxes. Media uploaded by apply is never deleted; Check Media is a manual step.
- Created notes are kept unless listed. "Unchanged" compares fields, tags, model and card ordinals/decks with the applied state. If no note carries the marker, the restore reports nothing to restore. Studied created notes have no removal tooling.
- Checkpoints are not created by restore or split. The caller supplies a verified checkpoint ID; WP-10 limits apply (no live export, whole-collection packages, presence and lower-bound scope checks). A split group uses one checkpoint for all units, and cross-group reuse passes only by age and protected-manifest match.
- Split limits: the group preflight is checked again by each unit when it runs, so a change between preflight and the anchor's turn fails that unit, not the group start. Only an update anchor is tested; a migrating anchor, grammar media and Application tasks in split groups are untested. Each invocation starts at most one new attempt per unit. Any restored unit marks the whole group `rolled_back`, and it can only be applied again through a new plan revision. A partial group is never rolled back automatically. `plans resolve` decision templates do not offer the `Anchor` choice for `GRAMMAR_SPLIT_NATIVE_REVIEW`; the request must be written by hand.
- Group rollback scans every journal head to find a group (bounded to 10000 matches), orders anchors before created notes by action and then operation ID, classifies stop conditions by error-code prefix, and silently keeps any item without a decision (it is absent from the results). Apply jobs (WP-13) do not exist yet, so only split executions or callers that pass a `group_id` form groups.
- Local durability windows remain. The restore intent, the restore snapshot and the first restore journal version are separate SQLite transactions, as are the restore commit and the apply operation's move to `restored` (resume finishes the latter). Orphan restore intents are not listed by `recover inspect`. The restore receipt is built by the application from its own read-back, not received from the companion ledger.
- Store visibility: restore snapshots appear in `snapshots list` with post-state status `unknown`, and `snapshots list --status` has no `restored` filter. Decisions are stored only inside restore intents; decisions for refused attempts are not kept.
- Retention: schema 11 records (`restore_operations`, `restore_receipts`, `split_executions`, `split_attempts`) are immutable and not covered by any pruning rule yet (WP-14).
- Concurrency: the second-writer rejection is the store lease only; native owner fencing, expiry and concurrent UI edits during restore are untested.
- Evidence breadth: one Anki build (25.09.2), one disposable collection, vocabulary notes only (no grammar or split groups natively), no AnkiConnect, no real process-kill crash injection. Crash boundaries are simulated with fake-port faults and test-only journal tampering; "disk full" is a held SQLite write lock. INV-13 is shown at the effect level natively and end to end only on the fake port.
- Settings: restore and split consume no settings directly; `backup.reuse_max_age_seconds`, `media.max_asset_mb` and the package limit are passed by the caller.
