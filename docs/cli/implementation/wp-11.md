# Implementation work package

Read [package dependencies and architecture](README.md) and the task-referenced OP/ALG records before coding.

## WP-11 — apply/reconcile

Touch: application existing commit orchestration, Anki native mapping adapter and journal. Read ALG-APPLY, ALG-MIGRATE, ALG-RECONCILE and OP-34, OP-59, OP-60.

Steps: implement [final native protocol](../decisions/native-bridge.md), including current invocation authority/approval/identity/source checks, one writer, fresh scheduler capture, snapshot+intent durability, media hash-safe staging, native mapped migration, exact field/tag/deck/task changes, operation-marker creation, actual final read-back and receipt. Remove unsafe generic “retry all/rewind committing” route from these use cases.

Tests: every forward-write failure matrix row, unknown add accepted, simultaneous writers, source edits, normal study between prepare/apply, profile switch, disk full after response, changed model, media collisions. Done only after fake boundary tests and disposable native retained-ID/history/scheduler evidence. Live writes remain gated otherwise.

## Completion audit — 2026-10-04

- Authority: `linguist_application::apply::apply_item` refuses without the current invocation's `apply` flag. It loads the exact plan revision and rejects a stale revision (a newer one exists) or a digest that does not match the recomputed approval digest. It requires a stored approval that covers this exact item and revision, and item content readiness from plan validation. Reviewed grammar split groups return `CAPABILITY_UNAVAILABLE` (ALG-SPLIT is WP-12). A committed item cannot be applied again, and an unresolved earlier operation blocks a new attempt until `recover reconcile`.
- Identity: a plan without a collection binding is weak and allows preparation/export only. The current execution binding from the native port must match the approval binding (endpoint, profile/path fingerprints, bridge, lineage). The endpoint must be loopback. The session epoch is checked by the checkpoint gate for new writes and by reconciliation, where a change needs an explicit `ResumeBindingDecision` with `--apply`.
- One writer: the call validates the held store lease, and the store rejects a second collection-writer lease. A native owner token (`labBegin`) is obtained before the first effect and released (`labEnd`) after durable accounting.
- Preflight before intent: exactly one installed model must match the target manifest exactly (absent: `APPLY_MODEL_MISSING`; differing: `MODEL_NAME_COLLISION`). The reviewed target deck must exist and must not be filtered. For an update, a fresh native read is compared to the captured source (fields, tags, model manifest digest, captured cards if present); any difference is `APPLY_SOURCE_CONFLICT`, and the original is untouched. Filtered-deck membership blocks. Every staged media asset must be in the local store with matching bytes. An existing collection file with the same name and the same SHA-256 is reused; one with different bytes is `APPLY_MEDIA_FILENAME_COLLISION`, and the plan must be revised. Required `labMutate` variants must be declared. A no-op update is refused.
- Mapped migration (ALG-MIGRATE): a model change needs explicit acceptance of the schema change and an explicit `SourceTaskMap` for the observed source model digest. Every observed card must map to a target task ordinal, or the item fails `APPLY_MIGRATION_DROPS_CARD`. The checkpoint must cover schema and the source model. Retained cards keep their IDs, scheduling and history in the desired post-state; newly enabled tasks are new cards with zero reviews.
- Checkpoint gate: `require_checkpoint` from WP-10 runs before any intent, with scheduling and media coverage, plus schema for migrations, and the note, card and source-model scope for updates.
- Snapshot and intent durability: the frozen intent (desired post-state, exact effect payloads, fresh pre-state with scheduling, checkpoint authorization) is stored in the new immutable `apply_operations` table (store schema 10). Then an immutable snapshot holding the freshly captured note, cards, scheduling and history is published, and then the journal. Each effect has `request_started` recorded before dispatch.
- Effects: `store_media` per new media file, then one `create_note` (the exact create-note wire envelope, validated by `linguist_anki::native::validate_create_note_intent`, with the `lab_op_<step UUID>` marker tag and expected absence) or one `update_note` (content precondition digest, optional migration with explicit ordinal map, all managed fields, added tags only, and one deck for every card). The native operation UUID is the journal step ID.
- Read-back and receipt: every step is verified only by an actual read-back that equals its expected projection. The final note projection is stored as an asset. The application builds a verified `NativeOperationReceipt` (note and card IDs, retained-history digest, model manifest digest) and saves it beside the untouched original snapshot. Only then is the journal committed.
- Failure handling: a native refusal counts as no effect only if the read-back still shows the precondition (`failed_before_write`, or `needs_recovery` with `APPLY_KNOWN_PARTIAL` after verified media). Lost responses, unknown or pending native status, read-back mismatch and local durability failure after dispatch all stop dependent writes and print `recover reconcile OPERATION --apply`. A known partial with only verified media can be superseded by a new attempt that reuses the media.
- Reconciliation (ALG-RECONCILE): `apply::reconcile` loads the same intent and journal and never creates a new operation ID. It checks identity, and a session change requires `--rebind` with `--apply` and a decision that names the current observed-state digest. For each unresolved step it reads native status and the collection: a matching read-back is adopted; pending is waited on; native `failed_before_write` with the precondition intact closes the step; an absent ledger row with the precondition intact and trusted lineage resubmits the same UUID once, journaled first; anything else needs review. An unknown status with no marker candidate is never resubmitted. Without `--apply` it only reports. A receipt saved before a crash is reused when finishing the commit.
- Batch: `apply_items` stops the group on identity, model, lease or local-durability faults, or on an unknown outcome, and continues independent items after other item failures.
- Store: schema 10 adds `apply_operations` and append-only `apply_binding_decisions` with immutability triggers, `approvals_for`, and a receipt epoch check that accepts an epoch adopted by a recorded rebinding decision.
- CLI: `apply PLAN [--revision N] [--digest D] [--item-id ID]...` is a local preview. It reports approval, readiness, action, target model and deck, media files, required variants and blockers, and exits 4 if any item is blocked. `--apply` returns `CAPABILITY_UNAVAILABLE` before any lease, checkpoint, journal or Anki request. `recover reconcile OPERATION` prints a local proposal for apply journals; `--rebind` needs `--apply`; `--apply` returns `CAPABILITY_UNAVAILABLE`. OP-34 and OP-60 are no longer unavailable routes.
- Native effects: `addons/linguist_bridge/effects.py` implements the create, update/migrate and media effects over an open collection, with the same precondition digest. It is not registered, dispatched or packaged.
- Generic retry/rewind: the new apply and reconcile code has no retry-all or rewind route. The only re-send is a same-UUID resubmission after evidence. `jobs retry` remains `CAPABILITY_UNAVAILABLE`.

Tests: `crates/linguist-application/tests/apply.rs` (26 fake-port tests) covers, against the failure matrix: backup absent, wrong binding or reuse rejected with zero mutation; source edited between preparation and apply (fields and model) as a conflict with the original preserved; study since preparation, with fresh scheduling captured into the snapshot and preserved; timeout after an accepted add reconciled to one note with no duplicate; an unknown add with an exact marker candidate adopted; unknown status without candidates never resubmitted; a lost request resubmitted once with the same UUID; copied markers blocking for review; disk full after native acceptance (simulated by a held SQLite write lock), with the result discovered by recovery and the snapshot untouched; partial native migration and study during mutation as `needs_recovery` without a success claim; profile switch and session change stopping until an observed-state-bound rebind; media collision without overwrite and identical media reuse; rejected creates; a known media partial being superseded; pending native operations; migration acceptance, completeness and filtered-deck blocks; mapped migration retaining card ID, history and scheduling; batch stop policy; immutable intent records; a crash after the receipt and before commit; authority, weak-binding, stale-revision, remote-endpoint, missing-variant, model and deck refusals; and a precondition-digest vector shared with Python. Concurrent writers are rejected by the store lease. `crates/linguist-cli/tests/apply_commands.rs` covers preview output, blockers, digest mismatch, `--apply` refusal with no journal or lease left, and the reconcile proposal and refusals. `addons/linguist_bridge/tests/test_effects.py` covers media rules and the shared vector. The disposable-native evidence is in [native apply effects](../evidence/native-apply-effects-2026-10-04.md).

Evidence: `cargo test --locked --workspace --quiet`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`, `python3 -m unittest discover -s addons/linguist_bridge/tests`, `python3 docs/cli/validate.py`, `git diff --check`, and the disposable Anki script named in the evidence record.

## Known limits — revisit after all packages

- No live mutation path. No Rust transport sends `labBegin`, `labMutate`, `labOperationStatus` polling or `labEnd`, and no `ApplyPort` adapter exists. The companion does not register these actions or dispatch `effects.py`. `apply --apply` and `recover reconcile --apply` return `CAPABILITY_UNAVAILABLE`. All orchestration, journaling and reconciliation is verified only with the fake port (WP-03/WP-13/WP-15).
- Wire contracts are incomplete. Only `create_note` has a strict shared envelope (Rust `validate_create_note_intent`, companion `payloads.validate_body`). The `update_note` and `store_media` bodies are the application's serde shape of `Effect`; they are not in the native-bridge decision, not validated by the companion ledger (which still rejects every variant except `create_note`) and have no strict Rust parser. `store_media` carries a local asset digest as `staged_asset`; there is no approved staging path or handoff of bytes to the companion, and `effects.store_media` takes raw bytes.
- Native atomicity is not established. `effects.update_note` runs `change_notetype_of_notes`, `update_note` and `set_deck` as separate backend calls outside a main-thread critical section. A crash between them leaves a partial note. The CAS is checked before these calls, not inside one serialized operation, so a UI edit can still interleave. Undo boundaries are untested.
- Model manifest digest agreement is unproven. The source conflict check compares the captured `model_manifest` with `ObservedNote.model_manifest_digest`. No native adapter computes that digest yet, and the evidence script uses a stand-in function rather than the AnkiConnect capture digest.
- Source conflict coverage is partial. Fields, tags and model digest are compared. Read capture records no cards, so card task and deck drift since preparation is not detected unless cards were captured. Source media bytes are not compared (capture does not archive media hashes). Anki's case-insensitive tag semantics are not modelled; tags are compared exactly.
- Cross-language canonicalization is proven for one precondition vector only. The companion's `jcs` is `json.dumps` with sorted keys, which differs from RFC 8785 for keys outside the Basic Multilingual Plane and for floats (neither is used today).
- Tags are only added. Planned tag removal is not represented in documents, so it cannot be applied.
- Deck mapping is per note, not per card or task. Every card moves to the purpose's target deck, or to the single existing home deck when no target is configured; several home decks without a target fail `APPLY_DECK_MAPPING_AMBIGUOUS`. A reviewed per-task deck map does not exist.
- Card generation is inferred. The desired cards come from rendered task ordinals. If Anki's template-emptiness rules generate a different set, the read-back mismatches and the item needs recovery; it is not reported as a success, but it is also not prevented in preflight.
- Study during the mutation window is not distinguished from migration damage. Any scheduler or history change between the fresh capture and the read-back enters `needs_recovery`. There is no rule that accepts append-only study after the native receipt, and no operator path to accept it.
- Migration limits: only an explicit `SourceTaskMap` is accepted; every source card must be mapped; there is no scoped destructive decision for dropping a task. The native migration maps no fields and then writes all managed fields, so source-only field content survives only in the snapshot archive. Reverse migration and restore are WP-12. `--accept-schema-change` exists on the CLI but is not consumed, because apply is gated, and no full-sync warning text is shown.
- Grammar split groups (ALG-SPLIT) are blocked with `CAPABILITY_UNAVAILABLE` (WP-12).
- Checkpoints are not created by apply. The caller must supply an existing verified receipt ID, and WP-10's limits apply (no live export, whole-collection packages, presence and lower-bound scope checks). New media names are not part of the checkpoint scope. No recovery group is built across items; `group_id` is passed through.
- Leases and owners: as in WP-10, the store lease token is validated but not proven to be the collection-writer lease for the bound lineage. The fake port only counts owner tokens; fencing, owner expiry and stale fenced requests are untested. The owner is released after accounting even when an effect is unresolved; companion behavior for that case is untested. Reconciliation without `--apply` takes no owner.
- Local durability windows remain. The intent record, the snapshot and the first journal version are separate SQLite transactions: a crash between them leaves an intent or snapshot with no journal. It is treated as never dispatched, but `recover inspect` does not list it. "Disk full" is simulated with a held SQLite write lock, not a real `ENOSPC` or fsync failure.
- Known partials stay pending. An operation with verified media and a native refusal of the note step remains `needs_recovery` in `recover inspect --pending` even after a new attempt supersedes it; there is no terminal "superseded" state. Uploaded media is never deleted.
- Resubmission safety depends on companion deduplication of the same UUID and payload. The ledger implements that only for queued `create_note` intents and has no live dispatcher.
- Review outcomes have no operator workflow. When reconciliation reports `review`, there is no command to adopt a differing state, record an observed-state-bound choice or export evidence; restore is WP-12. Only rebinding decisions are recorded.
- Rebinding is library-only. The CLI `--rebind` flag cannot construct a `ResumeBindingDecision` (no actor or evidence input), and live rebind is gated with the rest of reconciliation.
- CLI scope: the `apply` preview is local only. It does not check live identity, model, deck, media or source state, and reports `update_or_migrate` without resolving it. `recover reconcile` without `--apply` shows a local proposal, not the live matched/absent/partial/conflict evidence that OP-60 step 2 describes. Checkpoint and model journals report `unsupported_journal_kind`; model reconciliation still has no CLI.
- Batches are library-only. `apply_items` classifies stop conditions by error-code prefix. No CLI or job runs batches, and plan status (`applying`, `applied`, `partial`) is not recorded on plan revisions (WP-13).
- Settings are not consumed by apply: `anki.request_timeout_seconds` and `anki.commit_interval_seconds` (the mutation deadline belongs to the future adapter), `media.max_asset_mb` (the caller passes `max_media_bytes`) and `backup.reuse_max_age_seconds` (not passed by any CLI path).
- The receipt is application-built. The verified `NativeOperationReceipt` is constructed from the CLI's own read-back, not received from the companion ledger. Its evidence digest names the local read-back asset, and its history digest covers retained cards only.
- Identity checks: loopback is judged from the endpoint URL host only, with no same-host artifact accessibility check. `capability_digest` is not compared between the approval and execution bindings.
- Approval scope: any stored approval that covers the item is accepted. Approving a ready revision within the apply invocation (ALG-APPLY step 1 alternative) is not implemented. Duplicate decisions are not rechecked at apply beyond plan-validation readiness. Media MIME and role are not rechecked at apply.
- Evidence breadth: one Anki build (25.09.2) and one disposable collection, vocabulary only (no grammar apply), a synthetic Basic source (not the real Picture Words model), no AnkiConnect, no concurrent UI edits, no real process-kill crash injection. The failure-matrix rows for split children, restore, concurrent apply/restore and cache pruning belong to WP-12–WP-14 and are not covered here.
