# Research reference

### 1.2 Live API blockers and selected resolution

`apiReflect` shows `updateNoteModel`, `exportPackage`, `getActiveProfile`, `getProfiles`, `cardsInfo`, `changeDeck` and field/template mutation actions. **`createBackup` is absent.** The existing Rust commit path expects it and would fail before ordinary writes.

The installed add-on source `/home/lam/.local/share/Anki2/addons21/2055492159/__init__.py:849` implements `updateNoteModel` by assigning `note.mid`, replacing the field map/values, and calling `collection.update_note(..., skip_undo_entry=True)`. It does not explicitly call Anki's note-type migration operation or accept a card-template mapping. This observation does not prove corruption occurs, but it is insufficient to claim safe card/scheduling migration.

**Selected design:** standard AnkiConnect remains the transport for normal reads, additions, field/media writes and inspection. Old-note model migration requires a verified adapter using Anki's native note-type change operation with explicit field/template mapping and undo support. Current Anki exposes `change_notetype_info` and `change_notetype_of_notes`; their mapping semantics are documented in [Anki's own source](https://github.com/ankitects/anki/blob/main/pylib/anki/models.py). These are version-sensitive add-on APIs, so compatibility tests must target the installed Anki build.

Preferred route: a small, versioned compatibility extension in Anki's existing add-on process, invoked through the existing AnkiConnect transport where integration can be verified. It provides capability/version reporting, native mapped migration, verified backup receipt, and stronger collection identity. It is an internal bridge for Anki operations; the application remains command-only and starts no separate app server. The exact extension registration mechanism is an implementation spike, not an assumed supported AnkiConnect API. If this cannot be integrated safely, fail migration with instructions to use Anki's native Change Note Type; continue supporting preparation and new-note creation. Do not use direct database writes or blindly use the installed custom `updateNoteModel`.

The installed exporter supports `exportPackage(..., includeSched=True)`; its source uses Anki's package exporter. Use a scheduled deck export as the existing fallback backup path, then verify file existence/size and test restoration in a disposable profile. Do not claim that an export is complete merely because an API returned success. A `.colpkg` with media is the preferred whole-collection checkpoint for major migration. Anki's automatic/Create Backup backups include scheduling but exclude media; [Anki documents those distinctions](https://docs.ankiweb.net/backups.html). App snapshots additionally preserve all changed media.

The active profile name is available but is not a globally unique collection identity. The saved hash is an inspection fingerprint only. Until the compatibility adapter can identify collection incarnation, bind to endpoint/profile plus selected note/model manifests and block unexplained mismatch. Never infer collection UUID from the profile-name hash.
